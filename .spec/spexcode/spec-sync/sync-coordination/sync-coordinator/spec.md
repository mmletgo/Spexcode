# 持续同步中央编排

## raw source

一次高层需求应自动完成可信细化、实现、真实验收和可复核交付；暂停、取消、进程中断和输入变化不能重复副作用或用旧结果覆盖新输入。

## expanded spec

同一冻结 operation 的 code→spec 原生 P1 完整候选可复核本轮新提议的 code/derived missing_fact GAP。复用原 runner、request/session、fence、调用/返修预算和阶段 refs；严格核 original aggregate/local Git/独审、plan、readSet/selection、composed、完整输入与只读 Native 请求及正式结果。合法 repair 只派原 GAP owner 续稿并新独审，旧 accept 不改成失败；仍须当前严格 seal 和全部 P2 门。已复核的真实未知、冲突或无新发现保持原 blocked，冷恢复重验原结果而不重复模型调用；错绑定或无合法独审不能授予续稿。JSON合法但ID、边界或独立性协议未过时，在原预算下一attempt只续只读审查；previousReviewRef严格指向同operation较早的同候选失败原件，拒因和原输出仅在当次prompt现读，原owner批准保持。合法负例不走该续审。新 checkpoint 只引用已有结果原件和稳定身份，不重复归档诊断正文，不把临时诊断或草稿纳入产品 Git。

P0 后置回审先按实际受影响的冻结 owner 及 `refactor_business_meaning_changed` 发现筛选原轮。普通 P1 结构、测试绑定或审查诊断留在 P1。跨操作重验命中的 Git 草稿用原已认证 Native 任务的完整 targets 计算 owner，包括 P0 已审后才加入的规格叶，继续核原 schema、真实 Git 对象及保活引用。

Grok Build 的派发、候选和独审沿现有原生工作树编排。续用 Grok 格式拒绝前核对同一原生会话和 request ID。已停的只读复审在原候选下继续。

普通协调器显式启用[[sync-native-run]]的已结算工作树回收：completed及精确停止的failed/cancelled只在原请求/资源/Native和当前clean Git相符时正式close，原结果、错误、branch/archive、会话与JSON原件保持。P0/P1既有停止材料路径先完整认证Native/removed/request/owner/schema/保护面，再await[[archive]]临时checkout接缝；callback继续原physical/Git observer、capture及未批准provenance，空稿返回null继续来源顺序，观察或恢复异常亦只回收本次创建且经原归属证明的临时checkout。已捕获Git稿直接按对象冷读。dirty/未知停止保留，pending不改业务结果或预算；全程不启动旧Native、execution wake或队列，不增加扫描器或持久状态。

正式恢复复用同一回收入口，也检查本 operation 已 removed 但尚未 close 的原生工作树；仅从既有 attempt/resource 的冻结计划冷重放，完整请求、checkpoint、canonical 停止及 clean Git 门禁保持。removed 只结算容量，不独立授予删除；缺停止证明、dirty 或身份漂移保留，历史 failed 不补签。资源专用离线恢复继续禁止 Native/模型派发、队列和 execution wake。

只读P1返修的已审因果绑定与当前pending owner分开保存。正常重入即使已完成返修，也保留原readonlyOwnerRepair及其原readonlyBaseRef，历史latest repair-input已清空时只从同attempt已认证历史取最近完整绑定，不改旧CAS或以较旧绑定覆盖冲突。已审返修whole缺少该因果或与原owner/候选/独审不符时明确拒绝，不能回选较旧正文。

普通暂停恢复若没有新的修复输入，只能从原每组独审的冻结input或accepted provenance承接原诊断上下文。除此字段外完整当前输入须一致，再沿原Native请求、摘要、候选与停止原件严格认证accept。新修复输入、业务变化、缺证或漂移仍失效，不向fresh模型补旧诊断，不忽略repairContext或弱化digest。


事实继承资格通过既有checkpoint回调按acceptedRef精确命中本owner原local，逐字核完整changes、partition身份与批准状态，并复用elaborationGenerationSource认证原Native/Git来源，取实际generation attempt的V5而非复制wrapper的版本。new、prior重建和saved/accepted缓存共用此资格；当前V5、任意历史changes或草稿内容不能单独授继承权。原relatedIds只授权新差量，已批准旧事实只能作为确定值保留。

普通path#ID只读review诊断将已验证的原finding.affectedIds原样保存到既有ContractFinding.relatedIds，prose定位继续保同owner结构化映射。loadReadonlySpecRepair仅将已有relatedIds投影到已认证prior.changes的本owner唯一ID，原ReadonlyOwnerRepair/CAS保完整全局IDs及完整message；外owner-only为空但不删除finding，未知ID仍在完整原件门拒绝，局部不可见兄弟不当全局未知。[[sync-elaboration]]仅从该精确generationRef/reviewEvidence认证的当前readonlySpecRepair消费typed IDs，不从累计修复消息推断权限。旧已冻结诊断的relatedIds缺席不补写、不授事实权：冷验只在重算derived对照值中按saved对应finding的原始字段缺席窄投影该字段，随后仍完整canonical相等；已存在relatedIds及任何其它差异均不得忽略。同attempt的saved诊断只有在derived按原缺席投影后全部来源/候选/owner/reviewEvidence仍完整canonical相等时保原形状，来源不同明确拒绝。正常新attempt可从同一原合法review重新派生带relatedIds的新诊断，不改旧saved请求、原件或摘要。V1–V4及字段缺席不取得事实权限，旧V4的VERIFY续修提示保持。新V5事实资格参与返修inputDigest与缓存身份，普通无repair输入沿原摘要承接兄弟；旧批准owner按其真实sourceAttempt的原protocol重建输入冷验，只有新返修输入使用V5。writer33在任何写入前拒绝旧writer。

V3 正常运行、普通 recover 与 resource-only recover 共用可信注入的 [[verification-transport]]，不在 coordinator 重建远端执行器。原 operation/fence/attempt/runId/candidate/resource/receipt 保持；实际远端 evidence 仍需 V1/V2/V4 与当前写权才交付。resource-only 仅关闭和排空原绑定，不上传/create/start，不能用手工环境诊断替代正式 V3。

当前有效 attempt 的 V3 `recovery_required` stage 是待续观察，不是可永久复用的终态。普通重调度沿同一 [[verification-executor]] 资源桥恢复原 run/resource/checkpoint。原候选、请求、deadline 和失败 CAS 不变，新观察另存 stage，不为恢复重做模型或新建 run。原 deadline 已过的 planned 仅经原 target/daemon 的 closed、effect 排空及精确不存在结算 timeout，再确认 staging 清算后 removed 并沿原失败策略处理。不借用户取消赋予停止证明。锁未排空、未知 effect、身份失配或缺失 receipt 时仍 recovery_required 并保容量。此重入只处理当前明确 V3，不扩大历史资源回收为停止当前 Native。removed 重入只读原结论，不访问 driver/SSH 或补 checkpoint。

全局P1存在仅分析分区时，首次封口、封口返修及同operation的V1来源恢复重新核原P0 whole wrapper、原读集/基线、冻结计划与各区真实原件。跨attempt承接沿严格更早的正式provenance定位原分析和独审，复算独审覆盖及精确摘要。真实P1和认证的仅分析P0在原计划上互斥且完整，后者没有返修writer资格。同operation的code_to_spec即使原V1未通过，也只凭同P1原件造成的精确null扩域恢复原计划；V1候选及后续审查仍须真实重验。原P1局部输入、派发及V1–V4和交付门槛保持。

新的有效fence可沿原严格较新来源顺序读取已认证且正式stop/removed的精确物理JSON草稿；ZCode另须[[sync-stage-worktree]]规定的原精确turn.failed，原canonical cancelled不单独构成拒绝，普通暂停的turn.completed/turn.cancelled不取得此物理资格，既有正常Git暂停材料政策保持。P0保existingDraft来源截断，旧物理稿不因晚observedAt/mtime覆盖后来正常Git稿。仅owner draft可dirty，所有原request/dispatch/Native身份、source/tests/schema/context/index授权外变化及当前fence/lease/CAS门保持。新checkpoint仅记approved:false、sourceKind:physical_draft、原Native/stop引用、observedHEAD/tree、indexSHA与含原文的JSON材料CAS，不追补旧witness或将文件伪称Git稿/Native final。原errors及repairDiagnostics继续给新seed；P0 review仅续审且保原ready分析。P1通过内存binding/readonly seed/inputDigest/existingDraft回调精确定位旧稿真实Native attempt/round，仅严格较新的物理来源可替换；新旧程序可信readonly overlay按精确path/mode/OID投影比较，其余保护面不变，并完整保留原errors/冻结诊断；原文经真实Agent正常提交、原JSON/schema/业务/独审后才有新draft身份。writer27保护此准入，不授额外自动重试。

P1完整生成的`ac-test-flow-binding-v2`、`ac-test-flow-review-binding-v3`与`ac-test-flow-review-verify-repair-v4`在本owner尚未reserve时，可沿同一较新顺序和原停止认证读取[[sync-stage-worktree]]精确已提交草稿。若物理托管文件与 Git blob 有差异，由原冻结 seed 的隔离重建与完整双读认证后才冻结材料。`stopped_git_draft`记录approved:false、真实commit/tree/OID和index SHA、原Native计划/检查点/失败及材料CAS。原错误和诊断随同冻结到当前owner/seed，冷恢复用同一材料CAS重放原请求。已有reserved而未冻结此材料、旧v1、缺字段及P0仍使用原准入。原Native/Git见证与批准状态不补签。 仅P1阶段与原派发均缺席时，新attempt冻结v4归属提示版本。已有阶段按其原版本重建，已有reserved请求不补字段。

P1生成的ZCode `session/events` 精确超时也可沿上述已提交材料准入。沿P0相同的原typed失败、正式派发与结算核对，由[[zcode-structured-runtime]]只读确认原turn成功、idle、closed及停止。原任务、owner、计划、schema、只读overlay和保护树仍须相符。只有同一已停edit的正常后代HEAD存在唯一指定草稿的实际更新、工作树和index证明该Git对象时，才将原字节及真实失败诊断冻结为未批准材料。无合格提交时继续检查较早合格来源，保留原失败；不得使用未提交正文、赋予成功输出或继承批准。下一真实生成仍须提交、校验并独审。

上述观察只从通过原请求和停止身份认证的 ZCode Native root 派生原树槽供 [[content-filter]] 字节核验。共用 filter root 指针不能代替原身份。无可认证树槽时仍要求物理字节匹配 Git 对象。

P0 只在本次 attempt 尚无阶段检查点和 code_behavior saved/reserved 派发时冻结 git-json-v5。已冻结的 git-json-v1/v2/v3/v4、缺席字段及原请求保持精确恢复，未知传输在派发前拒绝。新运输沿 v2 正文和失败状态策略以及 [[sync-code-behavior]] 的只读自检，并在分析自检定位非 user:raw 验收变更的未变化只读来源。业务摘要、原草稿及已批准来源保持。真实草稿、审查结果、source/tests 保护及资源结算仍依原门核验。

显式 retryOf 只沿正式已结算祖先复用通过独审的局部 P0。冻结来源、输入、原意、计划、读集、业务基线、组合及局部 schema 和范围均一致时，认证原分析与独审、Git 原件和旧模型绑定，保存来源和原 resultRef。新操作只派发未批准分区，允许选择不同模型。原 attempt、调用、草稿及独审不补签。更早祖先因新准入被替代时，仍须重新核对已终结 attempt、活租约、资源和 journal 的结算。当前重新装配完整 P0；P1 仅分析资格及候选续验回到原操作复验该批准，全部当前封口和验证继续执行。

正式 retryOf 同样可保留尚未完成全图 P1 时已经独审 accept 的完整叶与父接口分区。沿既有已结算失败、取消及正式 superseded 祖先核对冻结计划、source、readSet、业务 selection、scope、组合树和完整局部输入；父接口分类及父子上下文必须相同。批准仍由原模型的实际生成与独立只读审查、完整请求摘要和 Git 草稿证明，原物理工作树已回收时从保活对象冷读。只保存原 resultRef 与真实来源，未批准 owner 使用本次模型继续；当前 schema、正文渲染及全图 seal 仍须重新核验。同 owner 较新的候选拒绝、错误或只读返修诊断阻止回退旧 accept，未采纳 settled 重验不得跨过去继承旧批准。历史字段、旧请求、调用及失败结论保持。

封口返修在复制载体找不到原Native生成时，沿同owner及同resultRef的正式provenance逐跳回到原生成和独立只读审查。每跳核原冻结计划、组合树、读集和业务selection，只承接严格较早且已结算的同操作轮次或正式重试祖先。草稿新鲜度以实际生成的operation、attempt及轮次比较，原批准与Git见证保持原样。

P0 分析的精确 owner 请求首次派发保留前，可沿既有 Native 停止资格观察原正常提交，复用 [[sync-stage-worktree]] 的已提交草稿核验，包括从原冻结树重建的托管投影。全量保护文件、索引与原停止身份均通过时，冻结真实草稿 Git 引用及当前 input、seed、owner、schema。续入先读取该冻结稿，旧已保留请求沿原规则。原稿仍待新分析及独审，原批准分区和诊断运输协议保持原绑定。

P1权限/绑定非法的独审沿[[sync-elaboration]]现有同owner repairDiagnostics重审原合法候选。续审保留原generation trace，不要求新review轮号存在generate；按真实session/thread/turn命中该operation原attempt实际dispatch，再冷验完整保存Native请求、原结果/summary摘要及Git草稿seed/result身份。只有当前局部完整输入与原candidate机械校验保持、原review重新判为越界/绑定非法时才跳过生成；旧seed排除draft的边界、原请求字段缺席、控制attempt跳过判据、预算/资源/取消及全图seal保持。多次续审与后续只读owner返修均追溯同一真实generation来源，不把新审查轮当新生成。

同一operation的P1已通过结构但未获得独审输出，若原独审因ZCode `session/events` 超时正式结算，现有repairDiagnostics也可仅重开独审。单体及分区均冷验原检查点、完整冻结输入、组合树、readSet与selection；分区同时核原计划及owner。原Native生成请求、summary及Git草稿须精确绑定同一候选。失败独审须有原只读请求、已启动的精确session/thread/turn、canonical失败及逐值匹配的正式removed/positive stopped原件；原失败保留，当前fence只沿现有provenance引用原resultRef。全局失败记录前暂停时，恢复须有同owner局部原件及同样完整的结算证明。较新生成派发或不同生成来源阻止旧候选优先，同一生成的只读续审被暂停仍可续审。其他方法超时、生成失败、业务repair、未知停止及跨operation按原准入处理。当前独审仍使用冻结提示政策，原请求和检查点无需补字段。

P1的whole缓存沿[[sync-elaboration]]同时核身份与当前owner范围。分区whole不直接继承ready，必须回原local input逐owner核缓存资格并重新严格seal；单体的当前saved与历史accepted入口均须消费资格结果。scope失效只放弃当前ready复用，优先沿既有草稿来源，必要时用已冷验缓存末轮Git稿继续，不丢JSON或改原reviewPassed/trace/ref，重新生成及独审后才保存新结果。

最终分区独审的程序字段格式失败沿现有reviewRepair续审同一候选。旧Native completed而程序曾接受的无效定位也只在原dispatch、request/input、plan、candidate、输出digest/trace及removed终态完整认证后作为未批准材料读取；不改旧status/resultDigest，不伪造rejectedOutput或Native失败。待处理只读发现必须先取得合法位置，格式错误先续该review组，已accept兄弟按原完整输入及原件严格复用；新稿校验通过的真实repair再回原唯一P1。缺原件、身份/候选失配、未知/重复affectedIds或错误path/ID不得因草稿续修扩大业务权限。原失败请求冷重建及已accept组来源重验从既有aggregate的p2SpecWritePaths恢复同一瞬态写范围，再调用共享请求构造接缝，不将可写owner套入只读定位约束。复用同一stage-worktree临时稿与现有refs，无DB版本或持久字段变更。
