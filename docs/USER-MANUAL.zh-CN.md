# SpexCode 用户使用手册

适用版本：项目 0.7.0 当前源码所提供的功能。更新日期：2026 年 10 月 15 日。

SpexCode 用于把软件需求、AI 开发任务和交付结果联系起来。你可以先说明功能应该如何工作，再让 AI 会话完成修改；也可以从已有代码出发，梳理它对应的业务约定。过程中，系统帮助你查看需求是否过时、任务由谁承担、有哪些未解决问题，以及成果是否真正完成验证和合并。

本手册面向项目使用者、需求维护者、开发人员和审阅者，只介绍业务概念、用户操作、处理规则及结果判断。命令是终端用户的操作入口；不涉及源码结构、接口设计或内部实现。

## 1 产品能帮助你完成什么

| 你的目标 | 使用的功能 | 应获得的结果 |
| --- | --- | --- |
| 看懂项目有哪些功能和约束 | 规格树、搜索、节点正文和图解 | 找到对应功能及其当前业务规则 |
| 让 AI 完成一项修改 | 新建会话、选择启动器、发送任务 | 一项可追踪、有独立工作区的开发任务 |
| 检查需求是否跟上实现 | 漂移检查、规格历史、变更预览 | 知道哪些约定需要复核及原因 |
| 记录问题并安排处理 | Issues、回复、指派、父子议题 | 留下问题、决策及承担任务的会话 |
| 判断成果是否可以采用 | 差异、证据、审阅、合并 | 确认改了什么、验证了什么，以及是否已进入主分支 |
| 让已授权范围持续保持一致 | 持续同步、业务裁决、验证和落地状态 | 在规定范围内生成、核对并交付一致的需求、代码和测试 |
| 向他人介绍项目 | Atlas、Flatcode、静态规格页面 | 一份可浏览的功能规格和图解 |

最常见的工作顺序是：**找到规格 → 明确需求 → 委派会话 → 查看进展和问题 → 审阅证据 → 合并成果 → 收尾会话。**

你也可以只使用规格管理，不启用会话、工作台或持续同步。各项能力可以按项目需要逐步接入。

## 2 使用前需要理解的概念

### 2.1 项目、规格和节点

**项目**是你要管理的一个软件仓库。一个项目有自己的规格、会话、议题和配置；同时打开多个项目时，先确认当前项目再操作。

**规格（Spec）**描述某项功能现在应该如何工作，例如用户能做什么、允许和禁止什么、什么条件下发生状态变化。规格也可以记录尚未实现的需求，但应明确它还处于待实现状态。

**节点**是一份规格在规格树中的位置。上层节点说明较大的业务范围，子节点展开其中的独立职责。每个节点有自己的标识、标题、正文和可选图解，可以被搜索、引用并查看历史。

### 2.2 会话、启动器和工作区

**会话（Session）**是一次持续的 AI 协作任务。它保留任务说明、沟通记录、工作状态和成果。停止一次运行不意味着任务记录消失。

**启动器（Launcher）**决定用哪一种已配置的 AI 工具及启动方式开展任务。同一工具可以有多个命名配置。选择启动器不等同于在 SpexCode 中直接设置模型参数。

**工作区（Worktree）**是会话开展修改的独立空间。它让不同任务的进行中改动相互分开。会话中的修改需要经过审阅和合并，才成为项目主分支的正式成果。

### 2.3 议题、证据和同步操作

**议题（Issue）**记录一个需要讨论、调查或解决的问题。议题可以关联多个规格，也可以分派给会话。规格表达约定，议题记录处理约定与现实之间差距的过程。

**证据**是支持结果判断的材料，例如测试结果、运行记录、截图、差异或可交互演示。AI 说“完成了”不等于已经提供充分证据。

**同步操作（Operation）**是持续同步中的一次可追踪处理。它包含所依据的需求、处理范围、执行状态、验证和交付结果。一次操作被受理、正在执行、验证通过和实际落地，是不同阶段。

### 2.4 各类使用者承担什么

| 使用者 | 主要职责 |
| --- | --- |
| 需求维护者 | 说明原始需求、补充业务事实、解决业务分歧 |
| 开发会话或开发人员 | 按规格修改，报告问题，提供证据并提出交付建议 |
| 审阅者 | 核对范围、差异和证据，决定是否请求合并或继续修改 |
| 项目管理者 | 接入项目、维护启动器与项目政策、安排协作和收尾 |
| 阅读者 | 浏览规格、图解和历史，理解项目当前规则 |

这些是工作分工。同一个人可以承担多项职责；它们不表示系统提供了一套按这些名称分配权限的账号角色。

## 3 首次接入项目

### 3.1 选择接入深度

| 接入方式 | 适合的情况 | 接入后的业务能力 |
| --- | --- | --- |
| 仅规格 | 先整理需求或理解已有项目 | 维护和检查规格，不改变 AI 工具的工作方式 |
| 规格与检查约束 | 希望在开发提交时执行规格检查 | 管理规格并建立提交检查，不向 AI 工具提供额外配置 |
| 完整接入 | 希望已有 AI 工具按规格工作，并逐步使用会话协作 | 规格、提交检查及所选 AI 工具的工作指引 |

终端对应入口如下。尖括号中的内容需要替换为你自己的值。

```sh
# 仅建立规格
spex init --pure --title "我的项目"

# 规格和检查，不接入某个 AI 工具
spex init --harness none

# 示例：接入你实际使用的工具
spex init --harness claude,codex --title "我的项目"
```

已有规格可以继续采用。完整接入会保留现有规格和用户自己的配置，不要求重新组织产品代码。使用完整接入时，须明确选择工具；不要因为示例列出两种工具就认为两种都必须安装。

### 3.2 开始前应具备的条件

项目需要由 Git 管理。使用命令行需要 Node.js 22 或更高版本；使用受管会话需要可用的会话运行环境和已安装、可登录的 AI 工具。当前推荐 Linux、macOS，或在 Windows 上通过 WSL2 使用会话能力；终端会话按项目要求准备 tmux。

首次接入通常由项目维护者完成。只阅读已经开放的工作台或静态规格页面，不需要在自己的机器重新接入项目。

### 3.3 打开工作台

安装用户可以使用以下入口；CLI 与工作台组件应使用匹配版本。

```sh
npm i -g spexcode
npm i -g @spexcode/spec-dashboard
```

在接入的项目内启动项目服务，再打开共用工作台：

```sh
spex serve
spex dashboard
```

每个在线项目需要自己的项目服务，同一台机器可用一个共用工作台查看多个项目。按启动输出提供的入口打开页面。新增项目不意味着要再开一份工作台。

首次接入后，维护者应确认项目名称、规格根节点、治理范围和启动器，并将应共享的规格与项目配置提交到项目历史。尚未提交的初始规格不能当成已建立的正式版本。

## 4 项目选择与管理

### 4.1 选择当前项目

在工作区的项目入口选择项目，或进入“全部项目”查看项目目录。目录显示已登记项目及其在线情况；已连接的其他机器按机器分组显示。

进入项目后，规格、会话和议题都属于这个项目。打开多个项目标签时，尤其要确认任务发往哪个项目。

离线意味着当前无法通过工作台访问该项目服务，不代表项目源文件已被删除。

### 4.2 添加或启动项目

在有管理能力的项目目录中，可以添加已有本地目录，按需要初始化 Git 或接入 SpexCode。创建新目录时，会自动建立 Git 项目，并完成不接入 AI 工具的 SpexCode 基础初始化。后续配置 AI 工具时，再明确选择所用工具或启动器。

建议按以下顺序操作：

1. 选择现有目录或新项目目录。
2. 确认是否已有 Git 仓库和 SpexCode 规格。
3. 新目录使用已经建立的基础规格；已有目录按需要完成接入，要配置 AI 工具时明确选择工具。
4. 启动项目服务。
5. 打开项目，检查名称、规格和启动器。

已有本地项目离线时，可通过其项目操作启动服务。远程机器上的项目只在在线时提供打开入口；当前页面不提供远程配置、初始化、密码修改或启动管理。

### 4.3 项目配置和密码

项目管理入口可以查看和编辑项目配置、执行诊断，并设置项目访问密码。管理员密码管理的是项目目录的管理入口，项目密码管理的是某个项目的访问，两者作用不同。

管理员密码未设置时，管理能力默认限于本机；设置后可按部署方式授权远程管理。访问协作工作台的人能够向 AI 会话下达指令，应按实际协作授权开放入口。

### 4.4 移除登记

项目目录中的“移除”是移除该项目的登记，不会删除项目源码或 Git 仓库。按页面要求输入确认文字后执行。不要将移除登记、停止服务和删除项目文件混为同一个动作。

## 5 查找和阅读规格

### 5.1 从功能名称找到节点

你可以从规格图谱逐层浏览，也可以通过搜索查找某个业务主题。选中节点可聚焦它，打开节点后阅读完整正文。

终端可使用：

```sh
spex graph
spex spec search "export"
spex spec owner <项目内文件路径>
```

搜索匹配规格中的表述；项目规格主要使用英文时，使用英文业务关键词通常更容易找到相关节点。知道实现文件时，“查看归属”可反向确认谁约束这份实现。

### 5.2 阅读顺序

打开一项陌生功能时，建议先读标题和一句话说明，再读当前正文，然后查看上层约束、相关节点和图解。实现归属帮助定位负责的范围；关联文件只提供补充背景，不能直接当成该节点治理的实现。

节点正文中有其他节点引用时，可以继续打开。文件和附件也可以打开为独立阅读内容，不会因为查看一个文件就丢失规格本身。

### 5.3 节点状态

| 状态 | 业务含义 | 使用时应注意 |
| --- | --- | --- |
| 待实现 pending | 需求已提出，但尚未形成相应实现或已提交版本 | 不应直接对外承诺为可用功能 |
| 进行中 active | 某个未合并工作区正在变更该节点 | 查看具体会话和待合并差异 |
| 漂移 drift | 相关实现晚于规格版本，规格需要复核 | 先判断业务约定是否仍成立 |
| 已合并 merged | 节点已有版本，当前没有检测到漂移或进行中的覆盖变更 | 仍应按实际业务场景判断运行结果 |

这些状态主要依据真实变更推导。手工写一个“完成”标签，不能替代实现、验证或合并。

### 5.4 图谱和图解的区别

规格图谱回答“项目分成哪些职责、它们处于什么状态”。节点内的图解回答“这个范围内部如何协作、流转或变化”。只有正文的节点同样可以完整表达业务，不是每个节点都必须配图。

## 6 维护需求和业务规则

### 6.1 一份规格应该写什么

一份面向业务的规格至少应说明：谁在什么场景下需要什么、允许做哪些动作、动作成立的条件、会产生什么结果，以及异常或冲突如何处理。

例如，“支持导出”不足以指导开发和验收。更清楚的需求是：“有查看权限的用户可以导出当前筛选结果；导出保留筛选条件；没有结果时提示空结果；无权限的数据不进入导出。”

规格写当前规则。规则变化时更新原文；历史交给版本记录，不在正文持续追加旧版、新版和过期解释。

### 6.2 让 AI 修改规格或实现

阅读当前节点后，可以把整个节点或选中的段落发给会话。说明你要解决的业务问题、希望改变的行为和验收条件。一个任务涉及几个独立职责时，让会话分别维护相应节点。

常见选中文本动作如下：

| 动作 | 适合的需求 | 结果 |
| --- | --- | --- |
| 发送到会话 | 提供一段上下文，请会话处理 | 选中内容和附言发往指定会话 |
| 编辑并发送 | 请求会话按附言调整 | 会话收到修改意图，开展相应工作 |
| 解释 | 只想理解这段约定 | 会话解释内容，该动作不要求修改规格 |
| 手工编辑 | 你已经知道准确的新措辞 | 直接编辑所选规格正文并保存 |

发送前确认接收会话。可以选择已有在线会话，或明确新建会话和启动器。是否在发送后跳转到会话，只改变阅读位置，不改变消息本身。

源码阅读中的选中内容也可以发送、请求修改或解释；源码面本身保持只读，修改交由会话完成。

### 6.3 手工保存的两种结果

**未启用持续同步时**，手工保存是规格正文变更，成功后形成相应提交和版本。它并不自动证明实现已经符合新需求。

**已启用持续同步时**，保存的正文意图进入同步操作，由系统进一步处理规格、实现、验证和交付。它不会先把新正文写入并提交到原输入工作区；保存反馈表示需求已关联操作，不表示原工作区已经更新或功能已落地。没有变化的保存不会派发新工作。

如果编辑期间原文已经变化，系统会拒绝直接覆盖。应阅读当前内容后重新判断修改。同步授权失效时，保存入口会给出实际配置问题，应修复并重新授权后继续。

### 6.4 业务契约中的细化内容

采用结构化业务契约的节点，可以进一步表达需求、流程、步骤、状态、事件、转移、规则、验收条件和验证绑定。你无需把实现函数逐个写成需求；重点是把用户行为和可观察结果说清楚。

契约阅读面可以查看这些条目、依赖和覆盖情况。这里有三个容易混淆的结果：

- **已经声明**：验收要求或规则已经写出来。
- **已经绑定**：已经指明用什么验证这条要求。
- **已经运行并通过**：确实执行验证，且对应结果有效。

页面显示“未运行”时，不能把前两项当作测试通过。原始需求草稿或带待决问题的草稿可以保存，保存成功不代表全部细化完成。

## 7 版本历史与进行中的变更

### 7.1 阅读节点历史

从节点历史入口选择某一版本，可以查看当时的正文，或查看该版本引入的变化，再返回当前版本。历史保留当时的标题、说明和内容，便于回答“什么时候改的、当时约定是什么”。

历史正文用于阅读；从旧版本选一段文字，不能直接当成当前正文执行选中编辑。

### 7.2 查看待合并修改

节点有进行中的修改时，待变更入口会显示相关数量。打开后，按工作区或会话查看新增、修改、删除、移动以及正文差异。

同一节点可以有多份会话提案。看到一份修改并不意味着它已经成为正式规格。仅存在于工作区的新节点，没有主分支正文，阅读时会直接展示它的提案。

### 7.3 看某一批提交改变了哪些规格

需要按一次提交或一段提交范围汇总规格变化时，可以使用：

```sh
spex spec report <提交或提交范围>
```

这用于回答“一批工作动了哪些规格”，与逐节点查看历史是两种阅读角度。

## 8 漂移检查与规格健康

### 8.1 漂移意味着什么

当被某项规格约束的实现发生后续变化，规格却没有同步更新，系统会提示漂移。漂移表明“需要复核”，原因可能是业务规则变了、实现偏离了约定，或者实现只是做了保持行为的调整。

如果规格明确约束某个具体单元，后续修改命中了该单元，未处理的漂移会进入阻断检查。只改到同一文件中的其他位置，或仅按文件整体关联的变化，通常属于提醒级别。提醒和错误应分别处理。

### 8.2 正确处理漂移

1. 阅读当前规格和实际修改。
2. 如果需求变了，更新规格，让它描述新的业务事实。
3. 如果实现错了，修正实现，使其重新符合规格。
4. 如果只改变实现方式、原约定仍然成立，记录真实的确认理由。
5. 再运行检查，确认阻断项已经消除。

```sh
spex spec lint
spex spec ack <节点ID> --reason "说明为什么现有业务约定仍然成立"
```

`ack` 会留下确认记录。只有实际核对过才能确认；它不会自动修正实现，也不能替代业务变更后的规格更新。

### 8.3 如何阅读检查结果

| 检查结果 | 业务含义 | 应采取的动作 |
| --- | --- | --- |
| 错误 error | 存在不能被接受的规格关系或未处理约束变化 | 修正后再提交或交付 |
| 警告 warning | 有覆盖、漂移或组织方式需要复核 | 按事实判断，安排治理，不直接视作功能故障 |
| 零错误 | 此次规格结构和一致性检查没有阻断项 | 继续检查真实业务行为与交付证据 |

常见错误包括引用目标不存在、同一标识冲突、节点关联不符合约束、明确约束的实现发生未确认变化。常见警告包括有实现尚未被规格覆盖，或需要复核的一般漂移。

### 8.4 项目诊断

```sh
spex doctor
```

诊断会帮助发现规格过于琐碎或拥挤、工具接入不完整、重复工作指引等问题。常规诊断只报告，不会替你改需求或修配置；规格健康建议也不等同于提交阻断错误。

## 9 创建和组织 AI 会话

### 9.1 新建会话

在会话页选择新建，输入任务说明，确认启动器并发送。通常按 Enter 提交，Shift+Enter 换行；输入法选词时先完成中文输入。

一份清楚的任务说明应包含：

- 要完成的业务目标和关联规格。
- 需要保持或改变的行为。
- 本次范围和不处理的内容。
- 用什么场景判断完成。

例如：“完善导出权限：用户只能导出有权查看的数据；保留当前筛选；补充空结果场景。请更新对应规格，提供操作证据，完成后提交审阅。”

终端也可创建并查看：

```sh
spex session new "明确的任务说明" --launcher <启动器名称>
spex session ls
spex session show <会话ID>
```

有多个启动器时，选择适合本任务的一种。未选择且项目未设置可用默认项时，需要先完成选择，不能假定系统会任意挑选。

### 9.2 指明相关规格和历史会话

任务输入支持节点引用和会话提及。输入 `[[` 可以选择规格；输入 `@` 可以查找会话；`/` 提供当前输入框可用的预设或命令。

普通节点引用和会话提及只提供上下文。正文中提到另一个会话，不会自动把消息发给它，也不会自动创建任务。实际接收者由输入框所在会话或明确的发送目标决定。

### 9.3 会话层次和并行任务

一个会话可以监督多个子会话，适合把独立工作拆开。会话树帮助查看谁发起了任务、谁负责监督。父级关系不意味着父任务会自动完成，也不代表父子状态相同。

调整监督者可以使用页面提供的移动操作，或：

```sh
spex session reparent <子会话ID> --to <新父会话ID>
```

重新归属不会重新启动子会话，也不要求原监督者在线。将会话从父级脱离后，它仍保留自己的任务与历史。

### 9.4 并发与排队

项目可以限制同时自主推进的会话数量，默认上限为 8。达到上限时，新任务可能排队，释放容量后再启动。

该限制针对实际推进任务所占的容量，不等同于会话总数。等待人回复、等待审阅或已经停止的会话，不应简单按列表行数理解为仍占用执行名额。

### 9.5 会话名称和定位

可以给会话改名，便于在列表中识别；改名不重写最初任务。终端读取或控制会话时，可以使用完整 ID、唯一 ID 前缀或分支名。在某会话自己的工作区中，`.` 表示该会话。

若前缀不唯一，应使用更长前缀或完整 ID，避免操作错目标。

## 10 与会话沟通和交付材料

### 10.1 发送补充要求

在目标会话的输入框补充需求、回答问题或要求修改。发送结果会反映消息是否已接受；已入队不一定表示 AI 已开始阅读和处理。

消息发送失败时，保留的草稿可用于修正后重试。对离线或恢复中的会话，应同时查看它的运行状态。

```sh
spex session send <会话ID> "补充说明或问题的答案"
```

### 10.2 会话中的几种阅读方式

| 阅读方式 | 用途 |
| --- | --- |
| Conversation 对话 | 阅读消息、回复、任务说明和结构化内容 |
| Terminal 终端 | 查看和操作支持终端的 AI 工具现场 |
| Diff 差异 | 查看该会话相对项目基线的修改 |
| 文件或网页资源 | 阅读会话交付的报告、材料或演示 |

无终端界面的启动方式使用对话面。默认阅读偏好可以在设置中调整；某个会话已经明确选择的方式会被保留。

### 10.3 向 AI 附加文件

新建任务和给已有会话发消息时，可以通过回形针、拖放或粘贴附加文件。上传完成后，材料引用进入草稿；**仍需发送消息**，才能把材料和任务一起交给会话。

上传进度可查看，失败时可重试或取消。新建会话可以先附加文件，再发送任务；已有会话的附件发往其所在机器，离线或归档的已有会话没有上传入口，应恢复后再附加。

议题中的附件作为议题证据链接保存，与发给会话的材料用途不同。不要把“材料已上传”当成“已经向会话下达任务”。

### 10.4 阅读会话交付的文件

会话可以发布文件，并在回复中给出可点击的文件引用。也可从会话文件列表按名称搜索、预览或下载。

文件发布登记的是当前文件位置，查看时读取当前内容，不是不可变的历史快照。文件被移动、删除或不可读时，引用会失效，应请会话修复或撤回。

会话执行者可以用以下命令发布并检查材料：

```sh
spex session files add <文件路径>
spex session files ls
```

发布后使用命令返回的 `[[file:<名称>]]` 引用，让阅读者从对话打开材料。该操作只登记调用会话的交付路径，不复制或上传文件内容。

工作台支持预览常见文本、Markdown、HTML 和 PNG、JPEG、GIF、WebP 图片；预览上限为 16 MiB。超出上限或类型不支持时，按提示下载查看。

### 10.5 网页演示和交互部件

网页交付表示会话发布了一个仍在运行的演示入口。打开时查看当前服务；发布本身不会替会话启动服务。服务停止后，演示入口也会失效。

交互部件可以把选择题、对照表或小型说明直接呈现在对话中。同名部件可由会话更新。部件把选择写入输入草稿时，仍由你检查并发送；页面上的选中状态本身不代表答案已经提交。

审阅较多截图、测试和运行材料时，优先阅读会话整理的一份完整报告，再按需要查看原始材料。

## 11 理解会话状态并处理异常

### 11.1 任务需要什么，与进程是否在线分开看

会话状态有两方面：任务目前需要什么，以及负责运行的工具是否在线。例如，“等待审阅”的任务可以在线，也可以已停止；它仍然需要审阅。

| 任务状态或显示 | 含义 | 用户通常应做什么 |
| --- | --- | --- |
| working / active | 正在推进，或本轮尚未声明结束 | 观察进展，按需要补充说明 |
| idle | 当前停在输入处 | 判断是否需要继续下达要求 |
| queued | 等待执行容量 | 等待，或调整任务安排 |
| asking | 等待人提供答案、方向或决定 | 阅读问题并明确回复 |
| parked | 等待已安排的后台任务或监督通知，会自行恢复 | 等待对应结果，必要时检查其等待原因 |
| review | 会话已提出合并审阅建议 | 看差异、证据和检查结果 |
| close-pending | 会话建议收尾关闭 | 确认没有剩余交付和决策，再关闭 |
| error | 某轮执行异常结束 | 读错误和已有成果，决定恢复或调整任务 |
| archived | 已执行关闭归档 | 从历史查看，必要时恢复 |

在线情况可能是 online、starting、offline 或 unknown。unknown 表示暂时无法确认，不足以证明任务已经停止。

### 11.2 等待人和等待后台的区别

当会话提出问题或交付材料等你决定时，它应处于 asking。你回复后才有新的推进依据。

parked 用于确有后台结果会唤醒的情况，例如监督中的子任务尚未完成。它不表示“正在等你批准”；也不应仅因状态看起来暂停就重复创建同一任务。

### 11.3 中断、停止、恢复和关闭

| 动作 | 对任务的作用 | 是否保留继续工作的条件 |
| --- | --- | --- |
| 中断 interrupt | 中断当前一轮执行 | 会话和工作区保留，可以继续沟通 |
| 停止 stop | 停止该会话的运行工具 | 工作区保留，可续接 |
| 恢复 resume | 重新启动已确认离线的会话 | 继续保留的工作和上下文 |
| 关闭 close | 收尾归档并移除会话工作区 | 分支、记录和对话保留，必要时可恢复 |

```sh
spex session interrupt <会话ID>
spex session stop <会话ID>
spex session resume <会话ID>
```

恢复用于已确认离线的会话。`--force` 是处理卡死会话的特殊选项，应先核对当前情况，避免重复启动仍活跃的工作。

关闭有正在执行的一轮时会被拒绝，应先停止再关闭。关闭过程会保存未提交工作的归档记录，不等同于把这些修改合并进主分支。执行关闭时应明确另一个目标会话；会话自身应提出关闭建议，由管理者收尾。

### 11.4 监控会话

页面显示当前状态；终端可以用一次性列表或查看命令确认当前事实。

```sh
spex session ls
spex session review <会话ID>
```

`session wait` 用于等待之后出现的可处理状态迁移，或发给调用者的消息，不是查询当前状态。某个会话已经在等待审阅时，等待命令不会仅因它已经处于该状态就立即返回。要判断“现在是什么状态”，查看列表或审阅结果。

## 12 议题管理与任务指派

### 12.1 什么时候使用议题

适合记录需要持续讨论、需要明确负责人、可能跨多个会话的问题，例如业务规则不清楚、缺少验收、发现缺陷或需要后续改进。

一次简单对话可以直接在会话里完成；需要留下可追踪处理过程时，再使用议题。创建议题不会自动把某份规格改成已完成。

### 12.2 浏览和创建议题

进入 Issues 查看列表。可以按打开或关闭、关键词、来源、标签、关联规格、作者、会话或父子关系筛选，再进入完整讨论。

创建时写清：问题是什么、涉及哪个业务范围、当前现象、期望结果，以及已有证据。关联规格有助于从节点反向找到尚待处理的事项。

```sh
spex issue open "问题标题" --node <节点ID> --body "现象、预期和证据"
spex issue ls
spex issue show <议题ID>
spex issue reply <议题ID> --body "补充事实或处理意见"
```

### 12.3 本地议题和外部议题

本地议题与支持的外部代码托管平台议题在同一工作流中阅读。详情标明来源，并为外部议题提供原平台链接。可选来源取决于该项目实际配置和可用驱动。

新建默认是本地议题，也可以明确选择可用的外部来源。本地打开中的议题可“提升”到外部平台；提升成功后记录外链，并将本地处理状态收尾。外部发布失败时，本地原议题保留。

为外部议题或变更请求注明关联规格时，使用其约定的 `Spec: <节点ID>`；多个节点用逗号分隔。外部平台的议题关闭，不会替代规格或代码成果的实际合并。

### 12.4 指派会话

把议题指派给已有会话，表示该会话负责接手。系统写入绑定并向会话发送接手提示；取消指派会移除绑定并发送相应通知。

```sh
spex issue assign <议题ID> <会话ID>
spex issue unassign <议题ID> <会话ID>
```

关闭归档的会话不能直接接手，应先恢复。重复指派同一关系不会重复建立任务。

议题正文中单纯提到某个会话，只是引用。需要派发时，使用指派或页面明确的发送动作。议题里的特殊 `@new` 派发入口可以在议题成功写入后创建并绑定新会话；它与普通会话提及不同。

如果绑定已经成功，但提示消息投递失败，系统会报告。此时应检查现有绑定并补充沟通，不能直接认定“什么都没发生”而重复创建任务。

### 12.5 拆分问题和记录关系

本地议题可以建立父子关系，以及阻塞、相关关系。未另选规格时，本地子议题可继承父议题的节点关联。外部议题不支持这套本地层次和关系操作。

子议题完成不会自动关闭父议题。父议题是否完成，仍需看其整体问题是否解决。标记重复会关闭当前议题，并把它指向保留的主议题，让后续讨论集中到正确位置；它不是让两个议题继续同时打开的普通关联。

```sh
spex issue close <重复议题ID> --duplicate-of <保留的主议题ID>
```

### 12.6 完成和关闭议题

关闭前应检查：问题是否解决、讨论中有没有未完成承诺、关联会话是否仍需收尾。存在承担会话时，页面会要求选择如何处理这些会话。

- 选择已自行声明可以关闭的会话，可以将所选会话与议题一同关闭。
- 选择仍承担工作的会话，会向它们发送收尾要求，议题继续打开，待它们交清工作后再处理。
- 不选择会话时，仅关闭议题。两类会话的选择互斥，不能一次混合处理。

议题关闭、会话关闭和成果合并是三个动作。关闭议题可能通知承担会话，但不会自动证明任务已合并；通知失败也不意味着议题关闭会被撤回。

## 13 审阅成果与合并

### 13.1 什么时候可以审阅

会话完成修改并提交后，可以提出合并建议，显示为 review。这个建议表达“请检查并决定是否采用”，不表示已经合并。

终端查看审阅材料：

```sh
spex session review <会话ID>
```

### 13.2 审阅者应核对什么

1. **任务范围**：是否完成原需求，是否混入未授权的新行为。
2. **规格变化**：当前约定是否准确，是否保留必要的上层规则。
3. **实际差异**：改动是否与报告一致，有没有遗漏或意外修改。
4. **验证证据**：是否真正执行对应场景，结果是否支持声明。
5. **交付条件**：是否存在未提交内容、冲突或阻断检查。
6. **落地位置**：成果停留在哪个工作区，是否已经进入主分支。

修复缺陷时，应有同一场景修复前失败、修复后通过的证据。新增业务应展示对应主流程和关键边界的实际结果。仅有“代码已改”或“规格检查通过”不足以证明用户行为正确。

### 13.3 要求继续修改

把具体问题发回原会话，说明不符合哪条业务约定、在哪个场景出现、预期结果是什么。会话重新开展工作后，应重新检查最终差异和新证据。

### 13.4 请求合并

```sh
spex session merge <会话ID>
```

这会把受检查的合并任务派发给原会话的执行者，不是绕过审阅直接修改项目。执行者需要同步最新基线、处理冲突并重新验证，再完成实际合并。

合并前的最新基线很重要：其他任务已经改变项目时，旧版本验证通过不代表组合后的行为仍正确。文本合并无冲突，也不等于业务验证通过。

主分支有未提交修改时，不应自动覆盖或混入它们。应先由相关使用者安排这些修改，再完成合并。

### 13.5 合并后收尾

确认正式分支包含成果、相关检查通过、没有待决问题后，再关闭会话和收尾议题。合并命令本身不会自动关闭会话。

不再需要合并的调查任务，也应把发现和证据交清；仍等待你阅读或决策的任务，应保持可继续回应的状态。

## 14 规格与代码持续同步

### 14.1 适用范围和启用条件

持续同步用于让明确授权范围内的需求、规格细化、实现、测试和结果持续对应。它支持从需求变化出发，也支持接入代码变化；正常且无业务分歧的处理无需每一步都请用户确认。

这是需要单独配置和授权的高级能力。当前已有执行、观察、裁决和交付入口，但整个产品范围的当前版本完整验收尚未完成；应按项目已配置、已验证的范围采用，不能据此推定任意项目都能全量自动同步。

启用前，维护者需要明确：

- 哪些节点和目录纳入同步，哪些材料只允许读取。
- 哪些业务事实和验收约定必须保留。
- 必须执行的验证、受保护测试和执行环境。
- 尝试次数、修复次数和总执行时间等预算。
- 哪个实际工作区被授权作为输入来源。

当前可登记的运行验证有明确支持范围：隔离环境中的 Docker Node `--test`。不能假定系统会自动识别和执行项目中的任意测试方式；缺少可信配置或运行条件会明确拒绝。

### 14.2 启用与首次运行

维护者先提交项目的同步政策。在项目目录启动 `spex serve` 并保持服务运行，再在另一个终端检查、授权当前来源并显式运行：

```sh
spex sync settings
spex sync enable
spex sync run <节点ID> --request-id <本次请求的稳定标识>
spex sync status --node <节点ID>
spex sync show <操作ID>
```

项目服务需保持运行，工作台可以关闭。正式服务观察已经授权的来源；不会因为发现一个新目录或新工作区就自动把它纳入授权。

纯粹提出一个尚无实现的新需求时，需要把其意图根纳入同步范围。状态中的覆盖清单会说明实际包含、仅作上下文、缺失或排除的部分。局部授权不能当成整个项目已经同步。

### 14.3 从修改需求开始

在启用同步的当前规格中保存需求，或显式发起同步后，系统围绕这次输入推进以下业务过程：

1. 细化需求、流程、规则、状态和验收要求。
2. 识别重大业务缺口或冲突。
3. 生成受授权范围内的规格、实现和测试修改。
4. 独立审阅，并执行适用验证。
5. 形成可检查的交付结果并按条件落地。

没有变化的保存不会反复启动新工作。同一请求标识和相同内容的重复提交会关联原操作；同一标识不能换成另一份需求。终端需要重放原请求时，保留并复用 `--request-id`；省略它时会生成新的请求标识。系统也可能把相同意图关联到已有操作；如果原操作失败或取消，重复保存不能当成已重新执行。

原生工作树同步默认沿用本机 Claude Code 配置。显式指定 `--model zcode:default` 或 `--model grok:default` 可以使用对应 CLI 的本机默认配置。切换一个已结束操作的执行器时，使用正式的 `--retry-of`，沿用原冻结输入和验收条件。

### 14.4 从代码修改开始

开发者可以通过“接入代码修改”或对应命令，把代码变化交给同步流程分析：

```sh
spex sync run <节点ID> --origin code
```

需求和代码同时变化时，使用 `combined` 来源。系统分析相对共同基线的业务变化，判断应更新哪些规格和验证。

代码里已经出现一个行为，不代表用户已经批准这个行为成为新需求。无业务冲突的实现调整可继续处理；真正改变或违反原意时，需要按具体分歧裁决。

### 14.5 处理业务缺口和冲突

**GAP** 表示影响业务决定的未知事项或缺口，例如缺少必要的业务事实。它阻塞依赖该事实的范围；无依赖的独立事项可以保留自己的推进判断。

出现业务分歧时，先查看原始需求、双方行为、相关规则、反例和待确认事实，再选择要裁决的具体项目。

| 裁决选择 | 你确认的业务方向 | 后续处理 |
| --- | --- | --- |
| 保持需求并修代码 | 原始约定继续成立 | 让实现回到原意，并重新验证 |
| 采用新行为并更新需求 | 认可分析中具体的新行为 | 更新相应需求和关联内容，再验证 |
| 输入新规则 | 两种现有表述都不足以表达目标 | 写清新规则，进入新的处理与验证 |

一次裁决只处理选中的分歧，不会替你默认批准其他项目。裁决后保留原需求和分析记录，并建立关联的新操作。正常无分歧的完成不需要额外批准。

### 14.6 四类验证回答什么问题

| 验证 | 面向用户回答的问题 |
| --- | --- |
| 结构验证 V1 | 需求、引用、流程、状态及验证关系是否完整有效 |
| 独立语义审阅 V2 | 细化和候选成果是否符合原意，有没有遗漏或冲突 |
| 真实运行 V3 | 适用验收绑定的命令是否实际执行并通过 |
| 当前性与交付核对 V4 | 结果是否仍对应当前输入、约束、依赖和真实交付 |

模型自述、规格 lint、确认记录或一串摘要都不能单独证明功能完成。任一阻断缺口、冲突、失败、过期或未结算交付都会影响完成判断。

### 14.7 正确阅读交付结果

| 看到的结果 | 已经意味着什么 | 还要确认什么 |
| --- | --- | --- |
| 已受理 | 需求已经关联一个持久操作 | 是否开始处理以及最终结果 |
| 某阶段 complete | 当前阶段通过 | 后续生成、验证和交付是否完成 |
| workspace_synced | 受管交付工作区已经形成同步结果 | 原输入工作区是否已采纳 |
| awaiting_landing | 交付存在，仍等待落地条件 | 未落地原因及所需处理 |
| source_synced | 完整交付已被原输入来源采纳，相关范围仍与已验证结果一致 | 正式主分支是否也已同步 |
| 主分支已同步 | 正式分支已经满足相应采纳及一致性条件 | 按本次覆盖范围理解结果 |
| stale 或过期 | 输入或相关条件已变化，旧结果不再证明当前版本 | 对最新输入重新处理 |

不要根据分支名字猜测结果。一个名为 main 的工作区不是交付证明；查看操作记录中的真实来源、交付位置和采纳状态。

面板中的请求差异表示“你提交了什么需求”，候选差异表示“系统拟修改什么”，完整交付差异表示“形成了什么交付”。三者不可互换。已结算交付可以打开实际正文和文件；尚未形成交付的私有工作区不能当作正式成果阅读。

交付验证通过且结算后，在面板点击“采纳到原工作树”，或执行：

```sh
spex sync adopt <操作ID>
```

系统只将干净原工作树安全快进到交付收据中的提交，正常执行项目 hooks。存在未提交改动、分支分叉或授权变化时会说明具体原因并保留交付，先处理该原因后再采纳。采纳后查看 `sourceSynced` 与 `canonicalSynced`：开发分支已采纳仍可能需要另行合并到正式主分支。

### 14.8 暂停、取消、恢复清理与重试

| 动作 | 作用范围和含义 |
| --- | --- |
| 暂停自动接入 | 暂停来源的新自动执行，仍观察并记录最新输入 |
| 恢复自动接入 | 扫描最新输入后继续，不自动解除单项操作暂停 |
| 暂停某个操作 | 控制该项已有操作 |
| 恢复某个操作 resume | 在条件仍有效时继续原操作，沿用原预算 |
| 取消某个操作 | 请求停止该项后续推进，仍需处理已发生的交付或资源 |
| 恢复清理 recover | 核对并结算已有资源或已开始的交付，不新开生成或验证 |
| 显式重试 retry | 符合资格时建立关联的新操作和新预算 |

```sh
# 来源级控制
spex sync pause
spex sync resume

# 某个操作的控制
spex sync pause <操作ID>
spex sync resume <操作ID>
spex sync cancel <操作ID>
spex sync recover <操作ID>

# 符合资格时显式重试
spex sync run <节点ID> --retry-of <失败操作ID>
```

需要恢复清理时，先查看诊断。清理完成不表示操作自动继续；再根据实际状态选择恢复、重试或提出新输入。

失败、取消或预算耗尽的操作，只有页面或详情报告具备资格时才能重试。输入已经变化时，应对当前输入提出新请求；未决业务问题和冲突不能靠随机重试绕过。改变执行预算也不会追溯扩大旧操作的预算。

### 14.9 持续观察和离线

观察面显示真实在线状态、最近完成扫描时间、来源和覆盖范围。旧记录曾经处于“观察中”，不代表服务现在仍在线。

自动接入暂停期间，系统仍记录最新输入；恢复时处理最新情况。服务停止后不再持续执行，重新启动时按已授权来源进行补偿检查。读取失败、来源失效或配置失效时，应按实际原因修复，而不是把旧状态当作仍在同步。

### 14.10 独立复核和撤销

跨机器或正式采纳前，可以对明确基线和候选做独立同步检查：

```sh
spex sync check --base <基线提交> --candidate <候选提交>
```

独立检查不依赖开发机当时的“通过”记录。可信政策不能由待检查的候选自己修改后用来免检；原始需求变化需要相应可信授权。

结果应区分“通过”“本次无适用变化”和“不支持或未配置范围”。无适用变化不等于已经执行并通过全项目验证。

对于已有完整交付记录且符合条件的成果，可以“生成成组撤销”：

```sh
spex sync revert <已采纳操作ID>
```

撤销会把相关规格、实现、测试和对应关系作为一组新的变更处理，保留历史和后续编辑，重新经过审阅、验证及落地。点击撤销或请求被受理，不会立即把主分支恢复到旧样子。

## 15 图解与已有仓库梳理

### 15.1 为节点补充图解

适合使用图解的情况包括：模块协作、业务流程、参与者交互、信息流转、状态生命周期。图解应服务于所在节点，不把所有细节堆到同一张图。

可以让已接入相应技能的会话执行 Atlas，为合适的节点画图、检查并交付。已有节点图解也可通过命令建立和检查：

```sh
spex diagram scaffold <节点ID> --type workflow
spex diagram check <节点ID>
```

支持的图类型有 architecture、workflow、sequence、dataflow 和 lifecycle。已有图默认不会被脚手架覆盖；重建前应明确是否要替换原图。

### 15.2 用 Atlas 了解项目

Atlas 可在支持的 AI 工具中作为插件或技能使用，帮助读取仓库、建立初始规格树和图解，再交付可浏览材料。在支持斜杠调用的宿主中，入口为 `/atlas`；其他宿主按自己的插件入口使用。

Atlas 适合首次理解或补全项目说明。生成的规格仍需按业务事实审阅；一张图存在，不代表图中功能已经运行验证。

### 15.3 用 Flatcode 批量梳理仓库

Flatcode 用于把已有仓库整理成可检查的规格树，并在有限轮次内反复补齐。

```sh
spex flat new <仓库地址或本地路径> --launcher <启动器名称> --lang zh
```

输入仓库地址时，会在隔离副本中开展梳理；输入本地仓库时，直接针对该仓库工作，要求它保持干净，并只允许产生规格范围内的修改。已有规格和启动器配置会保留。

默认最多执行 6 轮，以零规格错误和至少 90% 的覆盖作为收敛条件。达到轮数仍未通过时，结果会明确为部分完成，并列出缺项，不会把 AI 自称完成当成通过。

本地梳理会在当前分支提交规格成果，不会自动推送、发布站点或创建受管会话。开始前应确认目标仓库和当前分支。

### 15.4 输出阅读站点或合集

```sh
spex flat site <Flatcode结果目录>
spex flat gallery --out <合集输出目录> <结果目录一> <结果目录二>
```

前者生成单个仓库的静态阅读站点，后者汇总多个结果。部分完成的结果也可预览，并保留其覆盖情况。生成站点不等于自动对外发布。

## 16 公开阅读与远程协作

### 16.1 只分享规格

如果目标只是向他人介绍功能和规格，使用静态规格输出。它提供规格索引、节点正文及图解，不包含运行中的会话、终端、议题或项目管理写入能力。

```sh
spex graph --public
```

具体输出文件和页面选项可通过 `spex help graph` 查看。静态输出属于某次生成的内容，项目变化后应重新生成。

### 16.2 分享协作工作台

实时工作台支持查看当前项目、发送任务、操作会话及审阅成果。复制节点或议题地址，可以让有权访问同一服务的人直接定位到目标；分享地址不会自动授予访问权限。

项目访问密码和管理员密码按各自范围生效。公开阅读站点与可操作的协作工作台应按用途选择。

### 16.3 连接其他机器

需要跨机器查看项目或沟通会话时，先由有主机访问权限的使用者建立连接：

```sh
spex peer connect <SSH地址>
spex peer ls
spex peer disconnect <SSH地址>
```

建立连接需要本机工作台网关已运行，并具备对应 SSH 访问条件。连接由网关持有，可供后续会话复用。

项目目录能浏览已连接机器的项目，在线项目可以打开。它不是新增设备配对的页面，也不提供那台机器的项目管理按钮。连接不可达、远端网关未运行和凭据被拒绝，会分别反映为可诊断情况。

跨机控制某个会话时，使用完整会话 ID，避免把本机的短前缀误用到远端。

### 16.4 桌面入口

可选桌面壳提供同一个工作台的桌面窗口入口，并支持系统菜单、原生目录选择和深链接。已有工作台可被复用；外部链接交给系统浏览器打开。

桌面入口不会额外增加一套规格或会话。当前桌面实现不应视为已经提供正式签名安装包；分发方式和 Windows 下的 WSL2 环境按实际交付说明使用。

## 17 设置与自动化说明

### 17.1 个人阅读和操作偏好

设置页提供语言、主题、默认会话界面、终端字号和快捷键。首次语言按浏览器判断，可手工切换并记住选择。

默认终端或对话偏好用于尚未单独选择界面的会话，不覆盖你对某个会话已经明确作出的选择。快捷键可以重绑定或恢复默认；当前设置和快捷键说明是操作依据。

### 17.2 启动器与项目政策

维护者可查看并新增命名启动器，指定工具类型和启动命令，再在新建会话时选择。同一种工具可有多项配置。

启动器配置改变的是会话如何启动。模型名称、温度或推理档位若由所用工具管理，应在该工具或启动配置中维护；当前设置页不提供一套独立模型参数面板。

项目配置影响团队共同的名称、可用启动器、治理范围和工作政策。浏览器偏好影响个人阅读。机器专属路径和秘密不应作为可共享的项目事实填写。

项目配置编辑会核对版本；别人已经修改配置时，应先读最新内容再保存，避免覆盖对方变更。Issues 可由项目政策关闭，关闭后工作台隐藏相关入口，不等于删除历史议题。

### 17.3 自动化页面可以查看什么

自动化或 Plugins 页面用于理解项目的 AI 工作指引和检查：哪些规则始终提供、哪些技能按需使用、哪些动作在会话生命周期中触发，以及哪些检查有权拒绝继续。

可以搜索、筛选、选择一项并阅读其说明、随附内容和实际活动记录。活动数字有自己的统计窗口，不应当成全部历史。被当前启动配置关闭的检查会保留可见标记。

该页面是观察和阅读入口，不提供插件安装市场，也不提供直接新增、编辑或启停每项规则的开关。搜索筛选不会改变自动化是否执行。

### 17.4 退出 SpexCode 接入

```sh
spex uninstall
```

退出会移除 SpexCode 生成的接入内容和项目本地运行状态，保留项目自身的规格、插件意图和用户原文。它不是删除源代码或抹去已提交规格历史。

Git 检查钩子默认保留；需要一起移除时使用对应的 `--hooks` 选项，且只移除系统可确认未被用户修改的自有内容。退出前应先安排运行中的会话和需要长期保存的交付材料；保留规格不等于保留所有本机运行记录。

## 18 常见业务场景

### 18.1 新成员了解项目

1. 选择正确项目，先读根节点和主要业务分支。
2. 按自己的工作主题搜索规格。
3. 读当前正文，再看图解与相关节点。
4. 区分已合并、待实现和进行中的工作。
5. 不理解的段落使用“解释”，到会话阅读答案。

完成标准：能说明目标功能解决什么问题、主要规则是什么，以及尚有哪些待实现内容。

### 18.2 新增一项功能

1. 明确用户、场景、业务规则和验收条件。
2. 找到现有规格位置；独立的新职责建立自己的节点。
3. 创建会话并关联需求，也可通过议题安排处理。
4. 对会话提出的业务问题及时答复。
5. 检查规格、差异和真实运行证据。
6. 请求合并，确认主分支采纳后收尾。

完成标准：需求、实现和适用验证相互对应，正式分支已包含成果，未决事项得到明确处置。

### 18.3 修复一个缺陷

1. 记录当前现象、复现步骤和期望行为。
2. 找出约束该行为的规格；业务预期没变时保持其原意。
3. 交给会话处理，并要求保留修复前失败证据。
4. 让会话在同一场景验证修复后通过。
5. 审阅关联影响，合并并处理议题。

完成标准：原问题可验证地消失，相关边界未被破坏，不能仅凭提交了一段修改判断已解决。

### 18.4 会话中断后继续

1. 查看任务声明和在线状态。
2. 阅读已有对话、差异和交付文件。
3. 确认离线后恢复原会话；需要更换执行者时交接已有事实。
4. 说明尚未完成部分，避免重新执行已完成且有副作用的动作。
5. 重新核对当前输入和最终结果。

完成标准：保留已有工作，并能明确区分已完成、待完成和需重新验证的内容。

### 18.5 修改需求后自动同步

1. 维护者确认同步范围、验证政策和来源授权。
2. 在当前规格中保存明确的业务变化。
3. 查看关联操作的输入、范围和执行状态。
4. 有业务分歧时，只裁决具体冲突；无冲突则等待自动推进。
5. 检查验证结果、交付差异、来源采纳和主分支落地。

完成标准：当前输入对应的成果通过适用验证并实际落地。仅显示细化完成或交付工作区已同步时，尚不能宣称整个项目完成。

## 19 常见问题

| 问题 | 解释和处理 |
| --- | --- |
| 有规格是否表示功能已经实现 | 不一定。先看节点状态、实现归属和实际交付证据；待实现规格可以先存在。 |
| 节点是 merged 是否表示业务测试全通过 | 它表示规格版本和变更状态，不替代真实业务验证。 |
| 漂移是不是一定要改需求 | 先判断事实。可能需要更新需求、修复实现、调整归属，或确认原约定仍成立。 |
| lint 零错误为什么任务仍未完成 | lint 只覆盖其检查范围，还要看业务行为、适用测试、审阅和落地。 |
| 发消息后 AI 没立即回答是否应重复发送 | 先看接受结果和会话在线状态。已接受的消息可能在等待送达或下一轮处理。 |
| 在正文提到另一个会话是否就派发了 | 普通提及只是引用。使用明确发送、指派或特殊的新建派发入口。 |
| asking 和 parked 都像暂停，区别是什么 | asking 需要人回复；parked 等待已有后台唤醒，通常会自行继续。 |
| review 是否已经合并 | 没有。它是等待审阅的建议，仍需请求并核实实际合并。 |
| 关闭会话是否会把修改放进主分支 | 不会。关闭负责归档收尾，合并负责正式采纳。 |
| 为什么找不到已关闭会话 | 工作列表通常隐藏归档记录。打开归档列表，或使用 `spex session ls --all`。 |
| 交付文件引用为什么打不开 | 文件发布读取的是当前位置，源文件可能被移动或删除；请修复或重新交付。 |
| 上传完成为什么 AI 还不知道材料 | 上传只是准备附件，还需要把草稿作为消息发出。 |
| 子议题都关闭后，父议题为什么还开着 | 父议题按整体问题独立收尾，不由子议题状态自动关闭。 |
| 同步保存成功是否就是需求已重新执行 | 只表示关联操作。相同内容可能返回原操作，失败后的重新执行需显式重试并满足资格。 |
| 为什么同步按钮或裁决按钮不可用 | 查看真实原因，可能是只读视图、过期输入、授权失效、操作执行中或资源未结算。 |
| 为什么显示工作区已同步但主分支没变化 | 成果已在交付工作区，仍需满足来源采纳及正式落地条件。 |
| 能否靠重试处理业务冲突 | 不能。先补充事实或裁决，再处理相应输入。 |
| 恢复清理是否会重新跑任务 | 不会。它只结算已有动作；继续与新一轮重试是另外的选择。 |
| `spex help` 总览没列同步，是否没有这个功能 | 当前显式入口是 `spex help sync` 和 `spex guide sync`，按相应帮助和启用条件使用。 |
| 远程项目离线时能否在本机项目目录直接启动它 | 当前远程目录行只提供在线项目打开；远端管理需到相应机器执行。 |

## 20 常用操作速查

以下是日常用户操作入口，不代替各节的前置条件。`<节点ID>`、`<会话ID>` 和 `<操作ID>` 等均需替换；有实际修改作用的操作应对准正确项目和目标。

| 目的 | 命令 |
| --- | --- |
| 看全部命令或某项帮助 | `spex help`、`spex help session`、`spex help sync` |
| 看使用流程 | `spex guide` |
| 浏览规格树 | `spex graph` |
| 按主题找规格 | `spex spec search "业务关键词"` |
| 看文件归属 | `spex spec owner <文件路径>` |
| 检查规格 | `spex spec lint` |
| 记录约定仍有效的理由 | `spex spec ack <节点ID> --reason "真实理由"` |
| 看项目健康 | `spex doctor` |
| 新建任务 | `spex session new "任务说明" --launcher <名称>` |
| 看当前或全部会话 | `spex session ls`、`spex session ls --all` |
| 看任务原始说明 | `spex session show <会话ID>` |
| 给会话发消息 | `spex session send <会话ID> "消息"` |
| 会话发布并检查文件交付 | `spex session files add <文件路径>`、`spex session files ls` |
| 看会话审阅材料 | `spex session review <会话ID>` |
| 请求合并 | `spex session merge <会话ID>` |
| 停止或续接 | `spex session stop <会话ID>`、`spex session resume <会话ID>` |
| 收尾关闭另一个会话 | `spex session close <会话ID>` |
| 查看议题 | `spex issue ls`、`spex issue show <议题ID>` |
| 指派任务 | `spex issue assign <议题ID> <会话ID>` |
| 看同步当前状态 | `spex sync status --node <节点ID>` |
| 看同步详情 | `spex sync show <操作ID>` |
| 查看规格、同步、图解操作规则 | `spex guide spec`、`spex guide sync`、`spex guide diagram` |

与初始化、配置、文件交付或远程连接有关的完整参数，可分别查阅 `spex help init`、`spex guide settings`、`spex guide files` 和 `spex help peer`。项目介绍见 [中文简介](README.zh-CN.md)；开发贡献流程见 [贡献指南](CONTRIBUTING.md)。
