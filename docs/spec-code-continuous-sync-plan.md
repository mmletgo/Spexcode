# Spec 与代码持续双向同步方案

日期：2026-10-13

设计基线：SpexCode main，42f4cf169

交付范围：完整产品行为、业务契约、实施架构、阶段计划和验收标准；本文件不代表功能已经实现。

用户已确定的原则：正常变更全自动，业务冲突时确认；允许分阶段实施，不删减最终需求。

设计状态：业务闭环与技术可实施性独立审查通过。产品实施状态以 `.spec/spexcode/spec-sync/` 的权威节点及当前版本证据为准；设计审查不代表实现或全量验收通过。设计审查范围和已处理问题见第 17 节。

目标是让用户主要通过功能需求控制软件，同时允许从代码入口开发。无论从哪一边开始，系统都自动补齐另一边、详细业务逻辑和可执行验收，在明确的版本范围内验证一致性。正常路径自动写入实际文件；只显示提醒、补丁建议或 Agent 的完成声明，都不算完成同步。

## 1 完整需求和交付边界

| 编号 | 必须交付的能力 | 用户可观察的结果 |
|---|---|---|
| REQ-SYNC-01 | 修改 Spec 驱动代码 | 保存合法 Spec 后，自动定位受影响实现、调用 Agent、更新代码与测试；也可立即发起执行 |
| REQ-SYNC-02 | 修改代码反向同步 Spec | 人或外部 Agent 保存代码后，系统自动分析行为变化，更新对应详细 Spec、业务流程、状态逻辑及验收 |
| REQ-SYNC-03 | 从高层需求补齐业务主流程 | 用户只写功能目标，系统产出参与者、前置条件、步骤、业务规则、结果和失败出口 |
| REQ-SYNC-04 | 补齐底层状态业务流 | 对适用对象生成状态、事件、条件、转移、副作用、拒绝、重试、取消、重复与竞争处理，并关联实现和测试 |
| REQ-SYNC-05 | 持续保持一致 | 首次接入、实时编辑、外部提交、切分支、合并、恢复运行后都能发现并处理变化；新变化使旧同步结论立即过期 |
| REQ-SYNC-06 | 正常变更全自动 | 无业务冲突且输入完整时，生成、验证、修复及允许范围内的落盘连续执行，无需逐次批准 |
| REQ-SYNC-07 | 冲突可解释和可裁决 | 冲突展示原始需求、双方变更、受影响流程与证据；用户裁决后自动继续 |
| REQ-SYNC-08 | 完整追踪与真实完成状态 | 任一需求可追到主流程、状态规则、代码和运行证据，任何失败、过期、待裁决、待合并都不能显示为已同步 |
| REQ-SYNC-09 | 安全的并发和恢复 | 不丢用户编辑，不重复应用，不形成互相改写循环；中断、重试和回滚后可恢复到可解释状态 |

“一直同步”的产品含义是持续检测并自动收敛，而非人在输入一个字符时就瞬间重写全仓。系统明确显示同步中、需要输入或验证失败，只有当前版本通过全部适用检查才显示已同步。监听服务停止、Agent 不可用或业务事实缺失时不得虚报一致；恢复后自动补偿。

自动同步和主分支合并是两个结果。Spec、代码、测试在开发工作树中自动完成同步；合并继续遵守项目既有授权与门禁。本项目主分支存在未提交改动时禁止自动合并，完整结果保留在 worktree 中，显示“开发分支已同步，主分支待落地”。这项约束不把普通同步降级为人工改文档。

首次启用时明确输入工作树和受管交付工作树。受控编辑可以直接在受管开发环境闭环；外部编辑器保存也会自动触发并产出实际落盘的完整交付工作树。原始外部工作树是否已接收结果另行显示，不把“另一工作树已同步”冒充“原工作树已同步”。

## 3 权威关系和自动化边界

### 3.1 一份契约及其实现

保留以下依赖关系：

~~~mermaid
flowchart TD
  A[用户原始功能需求] --> B[详细业务契约]
  B --> C[主流程与业务规则]
  B --> D[对象状态与事件转移]
  C --> E[实现与测试]
  D --> E
  E --> F[运行证据与语义检查]
  F --> G[当前版本同步结论]
  H[人或外部 Agent 修改代码] --> I[分析行为差异]
  I --> J{与明确业务意图冲突}
  J -->|否| B
  J -->|是| K[用户裁决]
  K --> A
~~~

图中代码反向影响详细契约，受冲突规则约束。原始需求、详细契约和代码不能分别各维护一份相同业务规则；下层引用上层规则并增加必要细节。

### 3.2 已确认的决策表

| 情况 | 自动行为 | 需要用户处理的条件 |
|---|---|---|
| 用户新增或修改原始需求 | 补齐详细逻辑，更新实现及测试 | 缺少无法从上下文确定的重要业务事实 |
| 用户修改详细 Spec | 检查上层约束，更新实现及测试 | 新细节与原始需求或其他权威规则冲突 |
| 代码只发生内部重构 | 验证行为未变，必要时更新锚点与证据 | 无业务冲突时不询问，也不制造无意义文案变更 |
| 代码增加或改变了原始需求允许的行为 | 自动原位更新详细 Spec、流程、状态及验收并验证落盘 | 引入未经决定的重大业务政策时确认该政策 |
| 代码违背明确需求或现有显式规则 | 保留差异，产生冲突及失败证据 | 用户选择纠正代码、修改需求或给出新规则 |
| 同时修改两边，意图相容 | 自动整合，并验证组合后的行为 | 无需确认 |
| 同时修改两边，意图互斥 | 保留双方及共同基线 | 用户裁决具体分歧 |
| 同步 Agent 自己生成了不符合目标的代码 | 在同一任务中自动修复 | 修复预算耗尽或发现真正业务歧义时停在明确状态 |

“代码行为改变”不自动等于“新的业务意图”。必须同时检查原始需求、权威规则、既有验收和变更来源。人或外部 Agent 的无冲突代码修改可以驱动详细契约；系统自己的错误输出不能变成新需求来规避失败。

Agent 不得通过删除验收、弱化断言、放宽权限或改写原始需求来让验证变绿。原始需求需要改变时，将用户裁决作为新的意图输入，再自动调整全部下游。用户直接修改 raw source 本身已表达新意图，无需再次批准同一改动。

### 3.3 自动补齐和未知事实

可以自动决定有现有约定支撑、不会改变用户目标的实现细节。重要业务缺口必须明确列出影响、候选及推荐理由，只阻塞依赖该缺口的分支；独立分支继续推进。

例如“支持导出”可以推导出成功结果和失败反馈的必要性，但不能凭空认定谁有权导出、允许导出哪些数据、文件保留多少天。尚未明确的值不得伪装为已确认规则或用于发布实现。

## 4 业务契约的表达与追踪

### 4.1 Spec Markdown 仍是唯一可编辑的契约

保留 spec.md 及现有两段正文。为启用完整同步的节点增加简单标记 contract-schema: sync-v1，并在 expanded spec 内使用固定标题和 Markdown 表格。新增字段先在解析器、指南和 lint 中定义，再用于产品。

不再增加一份需要人维护的 contract.json。解析得到的契约图、影响索引、覆盖矩阵及流程图均为派生产物。流程图修改如要成为契约修改，必须经同一编辑入口回写 Markdown，不能单独形成第二份权威事实。

| 契约项 | 最小字段 | 用途 |
|---|---|---|
| REQ | 稳定 ID、目标、来源、约束、成功结果 | 保留用户意图，支持一段自然语言输入 |
| FLOW | ID、REQ 引用、参与者、入口、前置条件、步骤、终态 | 表达可完成的主流程与分支 |
| STEP | ID、所属 FLOW、动作、输入、输出、规则、下一步或失败出口 | 把主流程连到各模块职责 |
| STATE | ID、业务对象、含义、初始或终态标记、可见反馈 | 定义业务状态，区别于 Agent 运行状态 |
| EVENT | ID、来源、触发条件、输入 | 声明驱动状态变化的业务事件 |
| TR | ID、对象、原状态、事件、条件、目标状态、动作与副作用 | 定义合法转移、拒绝和幂等不变 |
| RULE | ID、适用范围、约束、依据、权威节点 | 一条规则只定义一次 |
| AC | ID、关联 REQ/RULE/TR、前置条件、动作、可观察断言、验证绑定 | 定义可执行验收，不能只写“功能正常” |
| GAP | ID、未知事实或冲突、影响项、证据、所需裁决 | 暴露无法自动确定的业务信息 |

结构只在能力适用时出现。无状态的纯计算功能可以没有持久状态机，但仍需输入域、结果、不变量、失败规则和 AC；“不适用”有依据，不能以空表通过检查。

标识符在标题修改或目录移动时保持不变；退役 ID 不再复用。复制节点必须生成新 ID；迁移记录旧节点定位与新位置，不能把当前目录名当作跨重命名的永久身份。

### 4.2 来源及依赖

每条详细规则记录来源种类和引用：用户需求、用户裁决、既有权威规则、可验证推导或代码变更。记录其 depends-on，支持从上层变化精确重算受影响细节。

来源决定可信边界，不直接替代验证。代码来源的规则仍需证明与原始需求相容；模型的置信度不能替代来源、断言或测试。

采用 REQ → FLOW/STEP → RULE/TR → 实现锚点 → AC → 运行证据的追踪链。方向可反查：一个函数变更能找到规则和需求，一个需求能找到全部实现及测试。

### 4.3 遵守现有节点治理关系

跨模块业务流程放在共同上层，引用权威叶节点；继续保留一个叶节点最多治理一个代码文件的约束，一个文件可在多个节点下以不同符号划分职责。

高层需求可以关联多个叶节点。每个叶节点通过 code 指向实际符号；related 仅作为上下文，不能计为实现覆盖。共享规则放在唯一权威节点，各实现引用它，不复制相近文案。

验收绑定是新增 AC 契约，引用仓库测试文件、稳定用例标识和已登记验证命令。当前代码没有规范化 eval 字段，本方案不复活旧 eval/measurement 模型。

### 4.4 完整性标准

对已声明范围，每个可达状态与每个相关事件都必须有明确处置：转移、拒绝、幂等不变，或说明为何该事件不适用于此状态。条件分支应覆盖成立、不成立及必要边界；一般自然语言条件无法机械证明互斥和完备，由语义审查及具体测试补足。

同时检查无法到达的状态、没有出口的非终态、没有触发来源的事件、未解释的副作用、失败后无下一步、跨对象不变量和关键事件竞争。合法终态允许无业务出边。

“全部状态流”验收覆盖已定义业务对象、适用事件及边界，包括系统主动发现的缺口。不能声称穷举任意现实环境中的无限状态；只要仍存在未处置的适用项，就不能显示该功能已完成。

## 5 从功能需求自动补齐业务逻辑

流程标识：FLOW-SYNC-EXPAND。

| 步骤 | 输入 | 自动产出 | 通过条件 |
|---|---|---|---|
| E1 识别目标 | 用户原文、已有 Spec 与代码上下文 | REQ、业务对象、边界与成功结果 | 没有把既有代码的缺陷当作目标 |
| E2 生成主流程 | REQ、角色与约束 | 入口、前置条件、步骤、结果和退出路径 | 用户任务能够从起点走到明确终态 |
| E3 识别适用边界 | 主流程及外部依赖 | 权限、写入、异步、网络、并发、外部回调等适用清单 | 每一项适用或不适用都有依据 |
| E4 展开状态 | 业务对象与事件 | 状态表、转移表、拒绝、取消、重试和幂等规则 | 相关状态与事件的处置无空缺 |
| E5 检查规则 | 主流程与状态流 | 不变量、条件边界、跨对象约束、业务 GAP | 不存在互相矛盾的规则 |
| E6 生成验收 | REQ、RULE、TR | 正常、异常、边界和竞争验收；测试映射 | 每条关键业务规则有可观察断言 |
| E7 独立审查 | 原始需求、候选契约、事实与验收 | 缺失场景、矛盾、未经授权的政策 | 阻断缺口已解决 |
| E8 进入实现 | 经检查的契约和影响范围 | 代码、测试、映射、运行证据 | 满足第 9 节完成条件 |

采用构建者和独立审查者两个职责。审查者从原始需求和适用性清单重新走业务路径，不只阅读构建者的“已完成”总结。可以由相同 Agent 引擎提供独立上下文，不强制用户购买多个模型。

修复具体缺口后复查受影响路径；发现新业务事实时重新展开受影响依赖。不能无限增加与用户目标无关的边界，也不能为了尽快结束取消已识别的必要状态。

## 6 Spec 修改驱动实现的主流程

流程标识：FLOW-SYNC-SPEC。

1. 用户在 Dashboard 或外部编辑器保存 Spec；自动模式会捕获稳定且可解析的内容，也保留“立即同步”入口。格式暂时不合法时显示具体位置，等待修正，不向 Agent 发送半截契约。
2. 将本次差异与上一次已验证共同基线比较，区分原始需求变化、详细规则变化及纯文案变化。纯格式变化仍更新版本关系，但无需重做行为实现。
3. 建立受影响闭包：直接治理节点、上层约束、引用该规则的流程、共享代码和相关测试。找不到实现归属时自动提出并验证归属；存在多种业务解释才询问。
4. 在受管工作树冻结输入，执行 E1 至 E7。上层变化使派生细节失效，系统重新推导并保留稳定 ID，不整体覆盖未受影响的人写内容。
5. 通过现有 session 创建和派发机制调用 Agent，携带需求差异、契约、允许修改范围、现有实现、验收及基线摘要。提示词表达任务，程序门禁负责执行范围与完成条件。
6. 自动实现代码，生成或更新针对性测试，并同步实际采用的详细逻辑。若实现揭示契约漏洞，回到细化步骤；不能自行改变已明确的用户目标。
7. 在冻结候选上执行结构、覆盖、语义及运行验证。可修复失败自动进入有限修复循环；环境问题、预算耗尽或业务冲突保留真实状态。
8. 检查输入和目标版本仍有效后，将 Spec、代码、测试作为同一候选交付。受管工作分支自动落盘并提交；源开发工作树按第 8 节规则回写。
9. 更新同步状态及证据。主分支是否已包含结果单独显示；正常同步完成无需用户再次点击“接受详细 Spec”。

Dashboard 的同步模式不能继续“先把新 Spec 独立提交到 main，再异步追代码”并把 main 显示为已同步。编辑应先进入自动创建或现有的受管开发工作树，用户仍在同一功能上下文中看到新需求和执行进度。

## 7 代码修改自动反写 Spec 的主流程

流程标识：FLOW-SYNC-CODE。下述“原位更新”指更新目标交付工作树中的权威 Spec 正文，而不是追加建议文档；外部输入树的安全写入边界遵循第 8.3 节。

1. 捕获人、IDE、外部 Agent 或 Git 提交带来的代码差异，保存 HEAD、index、工作文件与治理映射快照；不要求改代码的人必须由 SpexCode 启动。
2. 以最近一次共同验证基线分析差异。结合源代码、调用点、测试与运行行为，识别实现重构、合法行为变化、冲突或覆盖缺口；不能只把 diff 逐行翻译成自然语言。
3. 行为未变时保持业务正文稳定，更新失效符号映射和对应验证记录。
4. 行为变化且不违背原始需求或显式规则时，自动改写 expanded spec 的权威规则、流程、状态、边界和验收；更新依赖这些规则的节点。实际文件必须更新，不能仅生成“建议同步”报告。
5. 重新检查需求细化完整性。代码引入新的异步过程、状态或副作用时，相应的异常、取消、重复与竞争处理也必须补齐；缺失实现自动修复，无法决定的业务政策才提问。
6. 发现行为违反原始需求或明确规则时，生成业务冲突。展示“原来要求什么、现在实际做什么、受影响路径、支持证据”，允许用户选择修复代码、采用新行为并更新需求，或输入新规则。
7. 在同一协调操作中更新测试并验证。既有验收不能因为代码改了而自动删除；验收变更必须有合法规则变更作为来源。
8. 无冲突结果自动落盘并更新同步结论。裁决结果成为新的用户意图输入，自动重新细化和实现，无需用户手动修改多份文件。

“没有治理节点”的新功能也属于完整范围：系统自动定位上层需求并创建合适叶节点及映射，随后运行完整细化。若无法知道新代码服务哪个业务目标，则明确提出这一缺失事实，不把无归属文件略过。

## 8 持续同步协调和状态机

### 8.1 一个协调操作处理两边

引入 SyncOperation 作为一次变更的协调单位。文件事件只声明“需要重新协调”，不会分别启动两个互相监听的 Spec→代码和代码→Spec 自动化。

操作至少保存：操作 ID、根因 ID、来源、仓库与 worktree 身份及 generation、目标分支、输入快照、影响和读写集合、执行会话、阶段、预算、候选、验证证据、落盘与合并结果。

每次执行尝试使用独立 attempt 工作树；Agent 不直接拥有交付工作树的写入入口。协调器是唯一的回写和交付者，执行身份过期后拒绝接收其产物。生成后将候选固定为不可变 Git tree 或内容快照，验证在独立副本执行；旧 Agent 继续写旧尝试工作树也不能改变已冻结候选或有效目标。

实现必须在执行边界限制 Agent 的目标目录和 Git 交付权限，不能只在提示词里写“不要越界”。不能提供写入隔离的适配器不取得交付写权，由协调器隔离复制和受控应用结果；未知能力必须显示执行能力不足，不能悄悄按安全已满足启动。

入口先以仓库身份、分支/worktree generation、源快照、影响摘要和政策版本形成稳定接入键，通过数据库唯一约束归并重复 watcher、Git 和 API 事件；不能仅靠每次新分配的 operation ID 去重。操作内再以 operation ID、attempt 和输入摘要识别执行重试。已协调的相同字节为 no-op，不制造空提交。

自身写入只有在来源和实际字节都符合登记结果时才被归为本操作回声；Agent 运行期间的额外用户编辑仍然进入新输入。不能用一个“正在同步”布尔值忽略所有文件变化。

快照采集前后核对 HEAD、分支身份、index、文件集合和内容摘要，期间发生保存或切分支则重试，不使用前后不一致的混合快照。确认的输入保存为不可变 overlay，生成与验证使用相同输入。快照与 journal 是可恢复运行记录，不是第二份可编辑源码或业务契约。

同一范围尚未派发的编辑合并为最新快照；已运行操作的输入不可变，新编辑使旧操作失去写入权并触发后续协调。连续编辑时可以自动检查，不能强行写回尚未稳定的输入。

### 8.2 用户状态及内部阶段

| 用户状态 | 内部阶段 | 含义与后续 |
|---|---|---|
| 待同步 | detected、queued | 已发现差异并记录输入，等待稳定快照或资源 |
| 正在补齐业务逻辑 | analyzing、elaborating | 分析意图和影响，展开主流程与状态 |
| 正在同步代码与 Spec | generating | 在隔离工作树生成完整候选 |
| 正在验证 | verifying、repairing | 执行检查，基于明确失败自动修复 |
| 需要补充业务信息 | needs_input | 列明缺失事实及受影响分支，其他独立范围可继续 |
| 需要解决冲突 | conflicted | 双方意图或权威规则互斥，等待具体裁决 |
| 正在写入 | ready_to_apply、applying | 检查版本并应用已验证候选，尚不能显示完成 |
| 开发工作树已同步 | workspace_synced | 该工作树的实际内容与完整证据一致 |
| 主分支待落地 | awaiting_landing | 候选已完整验证，尚未满足合并条件 |
| 主分支已同步 | canonical_synced | 真实主分支包含候选，相关验证有效 |
| 输入已更新 | superseded | 旧结果保留供复用，但不可覆盖新输入 |
| 暂停中或已暂停 | pausing、paused | 继续记录输入，当前操作在安全边界停止；写入中的单元先结算 |
| 取消中或已取消 | cancelling、cancelled | 撤销尚未开始的副作用；进行中写入按第 8.5 节结算，取消不等于回滚 |
| 执行失败 | failed、budget_exhausted | 显示具体原因、证据、已保留结果及重试入口 |
| 正在恢复或需要恢复 | recovering、recovery_required | 核对真实文件、Git 和应用日志；未结算时不能变为已取消或已同步 |

这些是同步领域状态，不复用 session 的 active/awaiting 或节点的 active/merged。进程仍活着不代表业务同步成功，节点已经合并也不代表新版本的证据仍有效。

### 8.3 编辑并发与落盘

| 场景 | 处理规则 |
|---|---|
| 受管 attempt 工作树 | Agent 在授权范围内自动生成；协调器冻结候选、安排验证并交付到目标工作树 |
| 参与统一写入协议的开发工作树 | 冻结用户输入到隔离工作树，只回写 Agent 生成差量；不自动 stage/commit 用户原有改动 |
| 非协作外部编辑器所在工作树 | 作为输入自动生成并落盘到受管交付工作树；原树不被后台直接改写，明确显示待落地 |
| 原文件已被用户再次修改 | 旧候选过期；基于新快照重新整合，不能覆盖 |
| 多节点指向同一个文件 | 按实际文件和规则写入集合协调；不能只锁节点 ID |
| 独立节点或文件 | 可并行生成；交付到同一分支时再次组合验证 |
| 切分支、worktree 删除重建 | generation 变化撤销旧任务写入权；各分支分别维护基线 |
| main 前进 | 纳入最新 main，并重新验证受影响闭包 |
| main 有任何未提交改动 | 不自动合并，保留工作树，等待用户指示 |
| 同时存在 staged 与 unstaged 修改 | 保持用户 index 原样；新增自动差量留在工作树，不扩大提交范围 |

普通文件系统没有跨文件原子事务。外部编辑器也未必遵守本工具的锁；“读哈希再写文件”不能宣称是绝对 CAS。

受控 Dashboard 编辑走统一版本检查。只有能够让所有目标写方遵循同一写入协议，且在写入期间可强制独占的工作树，才允许后台原树回写。回写前记录 durable apply journal，保存原文、预期结果及每一步状态，进行写前校验、独占写入、单文件原子替换和写后核对。

短暂无文件事件不代表拿到独占写入权。无法约束外部编辑器时，系统仍全自动完成受管工作树中的 Spec、代码与测试，界面直接打开该实际结果；原输入树保持原样，交付经既有分支合并流程处理。不会用写后校验掩盖检查和替换之间可能丢失用户保存的问题。启用同步时即说明这一目标范围，无需对每次正常生成重复确认。

多文件写入期间保持 applying；重启时区分已写、未写、被第三方改动的文件。不能把两个先后提交或部分文件更新称为原子交付。受管分支的最终 Git 提交提供完整快照，主分支通过一次既有合并流程接收候选。

### 8.4 失败恢复与资源约束

操作登记与消息入队在同一数据库事务边界完成。执行租约带递增 generation，旧进程恢复后不能写入新任务结果。投递成功不等于生成、验证或应用成功。

副作用前登记意图，之后登记 receipt；崩溃恢复用实际 Git、文件字节和 journal 判断完成程度。覆盖提交完成但数据库未结算、文件写到一半、合并完成但会话未结算等窗口。允许重复计算，不允许重复应用或合并。

启动、分支切换、watcher 故障恢复及周期补偿都会重新扫描相关内容摘要，捕获停机期间与漏报的变化。后台服务不依赖 Dashboard 是否打开；服务未运行时界面显示监听离线，不显示“持续同步正常”。

冻结上下文超过2MiB时沿既有受限原生会话读取内容寻址的完整输入，生成与独审分别证明所需片段实际读取覆盖；不截断正文或读取未冻结宿主路径，取消与恢复仍受同一派发身份和预算控制。原生候选工作树放在外部runtime内，不在未初始化来源仓库创建`.worktrees/`。

复用 session 资源上限，为单操作增加可配置的调用、时间和修复轮数预算。相同输入和相同失败不会无限重启；输入、环境变化或用户重试才触发新尝试。预算耗尽保留结果，不能自动放宽需求或跳过验证。

### 8.5 暂停 取消和恢复的确定行为

流程标识：FLOW-SYNC-CONTROL。暂停自动同步保留文件观察和差异记录，只停止启动新的生成或交付阶段；当前操作停在下一安全边界。恢复后先扫描最新输入，过期候选重建，不直接继续向旧版本写入。

| 收到取消或暂停时的阶段 | 必须执行的行为 | 用户看到的结果 |
|---|---|---|
| 尚未进入 applying | 取消时撤销尝试的交付权并停止后续派发；暂停时保留检查点；隔离尝试产物保留 | 已取消或已暂停，目标文件未被本操作改写 |
| applying 已开始但尚未结算 | 记录请求并显示“正在完成当前写入”；不启动新业务阶段，完成已登记写入单元和字节核对后再停 | 不能显示已取消或已同步的中间半成品 |
| applying 中出现磁盘、访问或版本异常 | 进入 recovering；能安全完成时续完既定写入；无法完成则保留 journal 和前后版本，显示 recovery_required | 显示已写及未写范围、阻碍与恢复入口，不丢失证据 |
| 工作树已完成，尚未合并 | 取消剩余交付，不自动撤销已写入的完整候选 | “后续执行已取消，开发工作树结果保留”；main 不因取消而合并 |
| Git 落地已经开始 | 结算实际 Git 结果后停止后续操作；不以取消请求反向重写历史 | 明确展示是否已落地及撤销入口 |

取消只撤销尚未开始的业务副作用，不中断已经登记的短写入单元的完整性结算。此语义直接写在取消按钮的说明中，不额外要求用户批准正常结算。若用户需要撤销已经完成的结果，走第 12 节的成组补偿流程。

恢复过程中发现新用户版本时，保留双方快照，不把 journal 的旧 preimage 覆盖到新文件。重新建立最新输入并自动整合；若无法同时满足业务意图则进入 conflicted。执行环境尚不允许安全恢复时维持 recovery_required，并说明需要恢复的条件，不能静默将半成品标成终态。

## 9 一致性验证及完成条件

### 9.1 四层验证

| 层 | 验证内容 | 能证明与不能证明的事 |
|---|---|---|
| V1 结构检查 | ID、引用、归属、锚点、schema、图可达性、声明事件处置 | 证明契约结构完整；不能证明自然语言含义正确 |
| V2 需求与规则审查 | 详细逻辑是否服务原意、主流程是否可完成、规则和状态是否遗漏或冲突 | 给出基于具体证据的语义判断；不能代替运行测试 |
| V3 可执行行为验证 | AC 对应的单元、集成、产品路径、状态和竞争测试 | 证明规定场景在该候选上实际通过；不能以测试数量代替业务覆盖 |
| V4 版本与交付检查 | 当前实际内容、上下文、依赖及工具条件与证据绑定关系 | 防止过期结果、错误分支和未落盘候选被标完成 |

验证绑定到冻结候选：仓库及分支身份、相关 Spec/代码/测试、治理关系、上层规则和读集合摘要、必要依赖及验证配置。只记录 HEAD 或执行时间不够，未提交内容和工具环境同样影响结果。

结构结果由程序产生；语义结果使用结构化 verdict、规则/代码定位、原因和反例；测试由实际工具执行并保存退出状态及关键输出。Agent 的自然语言“已通过”没有完成权限。

### 9.2 同步完成公式

某范围的“已同步”必须同时满足：

1. 最新输入已被本次候选处理，候选真实写入指定工作树或主分支。
2. 原始需求、详细契约与实现之间没有未解决的业务冲突或必要信息缺口。
3. 每项需求有完整主流程、适用状态处理和实现映射。
4. 每条适用规则、状态转移、拒绝、幂等处理及关键条件分支有对应验收。
5. 必要测试和产品验证已在当前候选上实际通过。
6. 独立语义审查通过，没有靠删除需求或弱化验收换取通过。
7. 证据与当前文件、相关上下文及依赖匹配，应用 journal 已完整结算。

界面显示具体分子和分母，例如“本功能已声明的 14 个事件处置中，12 个有通过证据”；分母由契约和适用性检查推导，不能由 Agent 为了达标任意缩小。转移覆盖率不等于源码行覆盖率。

若权限变化、调用顺序或事件竞争属于业务规则，还必须覆盖其必要组合和顺序。状态机模型检查用于有限声明域，运行测试验证实现；两者均通过才可消除相应缺口。

### 9.3 与现有门禁和 CI 的关系

保留现有 lint、类型检查和相关测试。新增严格同步门禁对已启用同步的影响范围要求有效证据；Spec-only 修改目标后代码尚未完成，必须显示待实现并阻止以“同步完成”的名义落入受保护主分支。

门禁由受保护目标分支的可信校验器和政策启动。检查范围取共同基线与候选治理范围的并集；删除 schema 标记、节点、AC、规则或同步范围，移动文件、调整验证命令本身都属于受影响变更，不能据此让候选退出自己的检查。新政策必须经过适用的政策变更验证才成为后续基线，普通候选不能自行免检。

跨机器CI改变原始需求时，复用外部可信调用者选定的 `policyCommit`，从其普通UTF-8 Git blob `.spec/sync-intent-authorizations.json` 读取 `sync-intent-authorizations-v1` 登记。每项包含规范Spec路径、`beforeRawDigest`、`afterRawDigest`及裁决来源说明；新增、删除的一侧显式为JSON null，移动分别登记旧路径删除与新路径新增。程序复用Spec解析器规范LF并提取raw，精确匹配前后SHA256；缺失或错配即拒绝。结果给出精确摘要，受信维护者登记授权后自动重验；候选自行修改需求或补写登记不构成批准。SHA及来源说明不是身份签名，policyCommit必须由受保护目标或等效外部信任确定，不能取候选控制的参数。匹配授权只批准该原意差量，完整旧新raw、授权及输入摘要仍进入独立审查，旧稳定用例、VERIFY和保护oracle不获豁免。

当前受保护workflow从PR目标SHA构建可信校验器并选取policyCommit，核对实际合并候选的双parent，不执行候选workflow或安装脚本。原生独审使用已验证的macOS ARM64隔离适配器及固定Codex运行时，V3使用Linux Docker。所需runner与必需检查设置属于外部仓库配置；只有本地测试通过或文件已提交，不能表示远端保护已启用。

CI 验证实际待交付的候选或合并快照；验证后目标分支前进，按新的组合快照重验相关范围。需要保护分支时使用不可被该候选自行取消的必需检查入口，不能只把“已通过”状态写在同一可修改分支里。

长耗时 Agent 生成不放进 Git hook。Hook 给出缺失的同步操作及可恢复入口；同步服务提前完成候选和证据。普通工作分支允许保存未完成进度，主分支门禁检查完整交付。

Spec-OK 继续表示调用者确认契约未变，只能处理原有漂移机制；不能豁免新层的验收、冲突或过期证据。系统可以在确有完整行为未变证据时使用它，但不能盲目 ack 清掉错误。

现有 evidence blob 位于本机 Git common dir，不会随 Git 克隆传播。CI 必须在自身候选上重跑必要检查；若复用远端构建产物，应先验证其来源、输入摘要和检查版本，不能信任普通分支自行提交的“通过”JSON。证据缺失时重新验证，不以 hash 字符串代替真实证据。

## 10 产品交互

沿用现有 Spec 文档、变更面、会话和代码独立标签页，使用现有主题 token、字体和组件；不另造一套工作台。此交付定义交互行为，不包含可点击原型。

Spec 文档顶部展示当前作用域、监听状态、同步阶段、最新有效版本和必要的下一步。纳入范围的分子/分母不代表已经建立共同基线；来源工作树已采纳与主分支已同步从真实交付收据及当前Git读取，不能从候选完成或数据库阶段猜测。开发分支和 main 的结果分别标注，用户能够打开对应实际文件。

正文按“原始需求、详细流程、状态规则、验收与证据”组织，支持查看生成内容来源。人可以编辑任一业务层，保存后触发协调。图和覆盖视图从同一契约生成，避免维护两套相同内容。

变更面使用三个入口：需求变化、实现变化、验证结果；复用当前 diff 展示。用户可以由规则跳转到代码符号或对应测试，返回时保留原来的阅读位置。

同步控制包含立即同步、暂停自动执行、恢复、取消当前操作和查看失败原因。自动监听启用后保存即执行，普通成功不再要求点击“应用”；首次启用明确说明输入及交付工作树、作用分支、可写范围和 Agent 资源配置。暂停期间仍记录输入；写入中取消的进度和已落盘结果按 FLOW-SYNC-CONTROL 展示。

冲突面只展示当前需裁决的问题：共同基线、原始需求、Spec 变化、代码行为证据及影响。操作为“保持需求并修代码”“采用新行为并更新需求”“输入新规则”；用户选择后自动重跑受影响范围，历史裁决保持可追踪。

键盘可完成编辑、启动、暂停和裁决。状态不能只靠颜色区分；动态更新不会强制抢焦点或把用户正在阅读的内容滚走。复用现有响应式布局，窄视口以分步页面呈现同样动作，不删减能力。

CLI 和 HTTP 与 Dashboard 共用同一应用服务。服务在无浏览器时仍持续运行；界面只投影状态，不成为业务流程的必要条件。

## 11 技术落点与复用边界

以下为建议模块职责，实施时以实际导出和依赖校验为准，不承诺这些接口已经存在。

| 位置 | 责任 | 复用与约束 |
|---|---|---|
| packages/spec-core/src/contracts/ | 契约解析、ID/引用、纯结构检查、内容摘要及影响图 | 扩展已有 Spec/anchor 能力；不引入模型 SDK、网络或 Agent 调度 |
| spec-cli/src/sync/ | 观察输入、协调操作、细化、差异分类、派发、证据、应用和恢复 | 作为 Spex 采用层业务编排，复用 session 创建、投递及监督 |
| spec-cli/src/sync/store.ts 与 migrations.ts | 同步运行记录、读写租约、尝试、应用 journal、基线索引 | 复用现有 SQLite protocol 事务及组件迁移；不把 Spec 状态塞进 session 表 |
| spec-cli/src/spec-body-edit.ts | 复用范围/原文校验，抽出生成补丁能力 | 同步模式由协调器交付完整变更集；保留纯 Spec 模式的独立产品用途 |
| spec-cli/src/graphStream.ts | 共享文件观察输入和 SSE 刷新 | 抽取可复用 observer 订阅，避免另建一套 watcher；后台不依赖 UI 订阅 |
| spec-cli/src/sessions.ts | 工作树、会话、队列与实际 Agent 执行 | 不把业务契约解析混进大文件，新增编排由 sync 模块承担 |
| packages/session-application 等现有包 | 通用运行态、事务及投递能力 | 只增加必要通用接缝，底层包不理解 REQ、FLOW 或 Spec 内容 |
| packages/spec-core/src/evidence.ts | 内容寻址的证据 blob | 操作关联由 sync 存储负责；GC 保护仍被基线、候选或恢复任务引用的证据 |
| spec-dashboard/src/SpecView.jsx、ProseActions.jsx 及新同步组件 | 状态、编辑、变更、证据和裁决交互 | 使用同一服务，不在前端重复实现同步判定 |
| spec-forge 的后续 conformance 能力 | 消费相同判定协议及证据 | 本地同步不依赖 Forge；未来远端 PR 接入复用协议，避免循环依赖 |

协调器需要持久化运行过程，但 Git/工作文件继续保存 Spec、代码和测试事实。数据库中的“最后已同步”仅为索引，读取时必须结合当前摘要校验；数据库丢失不得以旧记录覆盖 Git。

建议持久化操作、尝试、范围租约、应用 journal 和 receipt 引用，不新增第二套源码、需求正文或消息队列。已有队列投递 envelope 带操作身份，使用现有幂等机制；运行记录与发送计划共享事务或使用既有事务消息接缝，不能出现操作已登记但永远未派发的窗口。

CLI 入口包含 spex sync enable、status、run、pause、resume、verify、decide、recover、revert、stop-writer 和独立 check。裁决和取消通过同一运行对象提供；合并继续走 session merge。具体参数、错误码和 HTTP schema 在实施对应阶段写入 guide 与契约，避免先维护两套相近命令。

配置分两类：版本化的自动化政策、适用范围、验证命令放项目配置；机器相关的 Agent 可用性、资源配置和运行路径沿用本地配置。不得在 Spec、日志或证据中存储模型令牌。

## 12 接入 迁移与回滚

首次启用先扫描既有 Spec 与代码，建立真实共同基线。原有文档不能因为存在 code 字段就被视为语义一致。系统自动迁移合适节点为结构化契约，并验证其保留原意；原先没有区分的正文不能无证据地全部标成人写意图或全标为 Agent 派生。

迁移在 worktree 中完成，保存旧文件与节点映射，允许按模块逐步纳入。迁移期显示“已治理范围”和“未建立基线范围”；整个项目尚有未纳入部分时不能宣称全项目已持续同步。最终全范围验收要求所有属于用户目标的业务区域都纳入，分批接入只是执行顺序。

数据库采用独立 spec-sync 组件的增量迁移，不修改既有会话数据含义。升级前备份并检查运行中操作；事务失败回滚迁移，恢复测试覆盖旧库升级、中断升级及重复启动。

回退版本先暂停新任务，结算或保留可恢复 journal，再停用同步写入者；数据库保留新增表和证据，不做破坏性 down migration。旧程序可以继续读取原有业务数据，但不得在未知新 schema 下继续同步写入。源码、Spec 和测试始终能通过 Git 还原。

版本回退先执行 `spex sync stop-writer`，持久暂停该物理来源并停止写入者；返回需要恢复的操作及真实资源诊断，不能把停止写入等同未知native资源已释放。原操作、journal、证据及新增数据库表保留，恢复仍走既有入口。

撤销一次已落地功能使用 `spex sync revert <operation-id> --request-id <稳定键>` 建立新的受控成组补偿操作，成组撤销 Spec、代码、测试与映射；不 reset 共享历史。相关内容有后续编辑时，根据当前版本生成补偿，不能覆盖他人工作。旧版本若违反当前需求，仍进入业务冲突处理。

未合并、含用户输入、正在恢复或被有效证据引用的 worktree 和 blob 不自动清理。清理在确认完整交付并可追溯后执行。

## 13 贯穿示例 后台导出任务

以下业务政策只用于展示本方案的表达和验收，不作为 SpexCode 或任一用户项目的默认政策。

用户输入：“用户可以在后台导出符合筛选条件的数据，任务完成后下载结果。”

系统先生成主流程：提交请求 → 检查权限及参数 → 创建或找到任务 → 排队 → 执行 → 发布文件或显示失败 → 查看并下载。随后识别任务为异步、有状态、存在重复请求与取消竞争的业务对象。

演示假定经用户确定：可取消排队或执行中的任务；失败后手动重试；任务 ID 保持、attempt 增加；同一幂等键和参数返回同一任务；完成与取消以先成功提交终态者为准。真实项目的权限、筛选快照时机、超时和文件保留政策仍须有来源。

| TR ID | 当前状态与事件 | 条件 | 结果及副作用 |
|---|---|---|---|
| TR-EXPORT-01 | 不存在任务，提交请求 | 权限和参数有效，幂等键未使用 | 创建 QUEUED，记录请求范围和 attempt |
| TR-EXPORT-02 | 再次提交 | 同一键、同一参数 | 返回同一任务，不重复入队 |
| TR-EXPORT-03 | 再次提交 | 同一键、不同参数 | 拒绝，原任务不变 |
| TR-EXPORT-04 | QUEUED，worker 开始 | 当前 attempt 有效 | RUNNING |
| TR-EXPORT-05 | RUNNING，执行成功 | 当前 attempt，尚未提交其他终态 | SUCCEEDED，发布一次结果 |
| TR-EXPORT-06 | RUNNING，执行失败 | 当前 attempt，尚未提交其他终态 | FAILED，保留可行动原因 |
| TR-EXPORT-07 | QUEUED 或 RUNNING，用户取消 | 有取消权限，终态尚未确定 | CANCELLED，禁止后续结果发布 |
| TR-EXPORT-08 | FAILED，用户重试 | 有权限且满足重试规则 | QUEUED，attempt 增加 |
| TR-EXPORT-09 | 任意状态，旧 attempt 回调 | attempt 不匹配 | 忽略状态变更，记录必要诊断，不发布文件 |
| TR-EXPORT-10 | 终态，重复回调或竞争事件 | 终态已确定 | 幂等不变或明确拒绝，不覆盖既有结果 |
| TR-EXPORT-11 | 任意用户操作 | 当前操作无权限 | 拒绝，任务和文件权限不变 |

“终态、所有事件”的表不能只靠一句“其他情况忽略”结束。生成完整状态×事件处置矩阵，细化哪些动作返回原结果、哪些应拒绝、哪些事件无效，并为重要处置关联 AC。

系统还应主动发现：请求成功但响应丢失后的重试、worker 崩溃留下 RUNNING、取消与完成的两种到达顺序、下载时权限变化、旧 attempt 成功回调、结果文件缺失。对于 worker 丢失后的超时和恢复政策，若项目没有既有规则，提出 GAP 并阻塞该路径完成；不能假装 RUNNING 永远会自动结束。

最终交付包含原始需求、细化后的主流程和状态契约、任务服务/worker/接口的实现锚点、真实测试及证据。若开发者后来合法地增加 PAUSED/RESUMED 行为，系统自动加入相应状态、动作、拒绝和恢复规则；若暂停行为与“必须立即完成”等明确原意冲突，进入裁决。

## 14 分阶段实施

所有阶段均属于同一完整目标。阶段验收只说明该部分成立，P1 或 P2 完成不能对外宣称全部双向持续同步已交付。

| 阶段 | 主要工作 | 本阶段必须验证的结果 | 依赖 |
|---|---|---|---|
| P0 基线与契约设计落地 | 细化本方案为 .spec 中待实现节点；定义 schema、ID、来源、同步完成语义及固定验收夹具；安装开发检查 | 现有主路径可运行；基线来源明确；原需求与全部后续阶段有映射 | 本方案 |
| P1 业务细化与追踪 | Markdown 契约解析、主流程和状态细化、适用性/GAP、AC、独立审查、图与覆盖投影 | 只输入高层导出需求，即生成完整主流程和适用状态处置；未知政策明确提出 | P0 |
| P2 Spec 驱动完整实现 | 先完成不可变输入、attempt 隔离、generation fence、实际 diff 范围校验、重叠写集合协调、幂等 receipt、最小 journal 与回声识别；再接入派发、实现、测试和落盘 | 改需求后自动得到详细 Spec、代码与测试；真实运行通过；失败不能削弱需求；基础中断、取消和过期写入测试通过后才开放自动落盘 | P1 |
| P3 代码驱动 Spec 更新 | 先验证共同基线与同时修改的组合验证，再接入行为差异分类、反向追踪、自动反写和冲突裁决 | 外部修改合法代码后交付工作树的详细 Spec 自动落盘；冲突只问具体分歧；两边同改能够收敛 | P2 |
| P4 持续运行与恢复 | 基于 P2 的安全原语完善后台订阅、补偿扫描、跨节点调度、外部输入、跨分支、预算、公平性和完整故障恢复矩阵 | 保存即触发，停机后补偿；无循环、无覆盖新编辑、无重复应用；故障窗口可恢复 | P3 |
| P5 产品交付与全量验收 | Dashboard/CLI 完整入口、严格门禁、CI证据、迁移/回退、完整真实仓库试用 | 第 15 节全通过，所有 REQ-SYNC 条目均有当前版本产品证据，才能宣布全部需求完成 | P1 至 P4 |

界面阶段不是最后才开始：P1 提供契约与缺口阅读，P2 提供进度和真实变更，P3 提供裁决，P4 提供恢复和运行状态，P5 完成所有入口的一致性验收。

可以并行：P0 后契约解析与验收夹具；接口明确后只读投影和编排；状态机稳定后故障注入与迁移测试。需求细化、协调状态和实际落盘的核心协议先由一个负责人确定，不能让多组同时创造不同事实模型。每个写入代理在独立 worktree 工作，边界清楚后再集成。

不在此给未经验证的日历工期。P0 确认依赖和运行成本后按工作包估算；估算变化只调整执行顺序和时间，不删除需求或把持续同步改成手动提醒。

## 15 最终验收矩阵

下面是产品验收，不是只检查函数是否存在。自动化测试使用临时 Git 仓库与 fake harness 控制故障；关键链路还必须通过真实受支持 Agent 执行，不能全靠 mock 宣称完成。

| 验收 ID | 场景 | 必须观察到的结果 |
|---|---|---|
| AC-SYNC-01 | 只写一段新功能需求 | 自动形成主流程、适用状态/边界、代码、测试和当前版本证据 |
| AC-SYNC-02 | 修改既有高层规则 | 所有受影响细节、实现及测试更新，未受影响内容保留 |
| AC-SYNC-03 | 修改详细状态转移 | 对应实现与条件分支更新，上层意图仍成立 |
| AC-SYNC-04 | 外部编辑器修改合法代码行为 | 受管交付工作树的权威 Spec 自动更新并验证，UI打开实际结果；具备协作写入协议时可自动回写原树，其他情况下明确原树待落地；不要求手工改文档 |
| AC-SYNC-05 | 纯内部重构或符号重命名 | 验证行为未变，更新映射；不制造虚假需求变更 |
| AC-SYNC-06 | 代码违反原始需求 | 出现有证据的冲突；原始需求和验收未被偷偷改弱 |
| AC-SYNC-07 | 用户裁决冲突 | 裁决成为新输入，自动完成全部下游并验证 |
| AC-SYNC-08 | 重要业务事实缺失 | 精确 GAP 阻塞依赖范围，独立任务仍执行，不编造默认政策 |
| AC-SYNC-09 | Spec 与代码同时相容修改 | 一个完整协调结果，无相互覆盖或重复提交 |
| AC-SYNC-10 | Spec 与代码同时互斥修改 | 展示共同基线、双方意图与影响，等待裁决 |
| AC-SYNC-11 | Agent 自身反复写入两边 | 回声归入原操作，不形成无限同步；期间的人类编辑仍捕获 |
| AC-SYNC-12 | 用户在生成后继续编辑，或旧 Agent 恢复写入 | 旧候选失去写入权，旧 attempt 无法修改冻结候选与交付树，最新输入重新协调 |
| AC-SYNC-13 | 新文件、新功能、节点移动及删除 | 创建或迁移治理关系，追踪 ID 连续，无悬空引用 |
| AC-SYNC-14 | 跨模块流程或共享文件变更 | 完整影响范围被处理；共享规则唯一，合并后一起验证 |
| AC-SYNC-15 | 切分支或删除重建 worktree | 旧任务不能写到新身份，各分支同步结论独立 |
| AC-SYNC-16 | main 前进或存在未提交改动 | 前进后重验；dirty 时不自动合并，完整候选可查看和恢复 |
| AC-SYNC-17 | 已有 staged 与 unstaged 修改及非协作外部编辑 | index 和用户内容保留；协作树仅写生成差量，非协作树自动得到实际受管交付版本且原树不被覆盖 |
| AC-SYNC-18 | 生成、逐文件应用或合并结算期间崩溃 | 重启核对实际结果，恢复或报具体冲突，无重复副作用 |
| AC-SYNC-19 | 重复事件、请求和消息投递 | 最多一次实际应用与交付 |
| AC-SYNC-20 | 服务停机、watcher 漏事件或外部提交 | 恢复/补偿扫描发现差异并自动处理 |
| AC-SYNC-21 | Agent 不可用、测试工具失败、预算耗尽 | 真实失败及可恢复产物可见，不显示已同步 |
| AC-SYNC-22 | 测试通过后相关依赖或政策改变 | 旧证据过期，重新验证；无关修改不强制全仓重跑 |
| AC-SYNC-23 | 只提交新 Spec 而实现未完成 | 受保护主分支门禁拒绝虚假完成，UI显示待实现 |
| AC-SYNC-24 | 迁移、回退或撤销已落地功能 | Spec/代码/测试/映射成组处理，历史和用户修改保留 |
| AC-SYNC-25 | 导出业务的成功、失败、取消、重试、重复和竞争 | 已声明事件处置和必要顺序均有实际通过的测试，未决政策不算通过 |
| AC-SYNC-26 | 无 Dashboard 的持续运行和 CLI 操作 | 同样自动同步、恢复、裁决和查询，UI不成为必要依赖 |
| AC-SYNC-27 | 全项目覆盖、跨机器 CI 及候选修改治理政策 | 未纳入范围明确显示；最终所需范围全部纳入；CI独立验证；删除标记、AC或改变命令不能自行豁免门禁 |
| AC-SYNC-28 | 写入前、写入中、写入后取消，暂停期间继续编辑后恢复 | 写入前不产生目标副作用；写入中完成结算或明确需要恢复；写入后保留完整结果并停止后续交付；恢复只处理最新有效输入 |
